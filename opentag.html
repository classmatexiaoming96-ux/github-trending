一句话定位

让 Slack/GitHub/Lark 里的 @opentag fix ... mention 触发本地 Codex/Claude Code，在 git worktree 隔离环境里跑出 patch，再把 diff/PR 回写到原平台——一套跨平台的"agent invocation 协议"。

核心抽象：OpenTagEvent 是从 Slack/GitHub/Lark webhook 归一化后的"原始 mention 事件"；ContextPacket 是给 executor（Codex/Claude Code）使用的"裁剪后上下文"（summary + selected sources + facts + exclusions）；OpenTagRun 是一次完整的"用户 mention → executor 执行 → 结果回写"生命周期。整套系统的设计目标是：让 mention 成为 Agent 的一等公民。

为什么是 mention 而不是 API？

传统 bot 通过"slash command + 私有 API"接入——开发体验差、用户要记语法。OpenTag 走 Slack/GitHub 原生 mention，人类和 agent 共用同一条消息。@alice @opentag 这个代码会怎么报错？@opentag 看到 fix intent，@alice 看到同伴提问。两个 recipient 并存，互不干扰——这是 OpenTag 的根本设计哲学。

mention 解析 · 5 intent + 12 flag + scope 校验

@opentag/core/src/mention.ts 537 行——把任意 Slack 消息体里的 @opentag ... mention 解析成结构化 OpenTagCommand。这是协议的"前端 lexer"。

5 种 Intent 类型

fix（修 bug）、review（评审代码）、investigate（调查问题）、explain（解释代码）、run（执行命令）——不在列表里的会被标 unknown intent，进入 generic command path。未知 intent 不报错，但执行器会按"general command"模式跑，缺少针对性 prompt。

12 个已注册 flag + 单值/多值区分

approval、executor、file、label、line、network、path、range、runner、scope、timeout、url。SINGLE_VALUE_FLAGS 集合把 approval/executor/line/network/range/runner/timeout 标为单值——重复赋值时收集诊断信息（level=warning）而不是后写覆盖。

从 OpenTagEvent 到"给 executor 的 prompt"中间要经过 7 个阶段，每个阶段都有 hooks 注入点。这是 OpenTag 协议最复杂的部分。

ContextSourceClassification 的语义

四分类不只是"重要不重要"，而是直接影响 packet 在 executor 侧被渲染的方式：

function contextPacketSourceRole(classification: ContextSourceClassification): "primary" | "supporting" | "background" {

      return "supporting";       // 标注 role=supporting，可选注入

    case "sensitive_material":

Policy 解析的 5 级 scope 优先级

policy 不是"全局一种"——它有 5 层级的覆盖优先级，从低到高：organization_default < adapter_surface_default < work_context_owner_container < work_item_override < primary_anchor_override。越靠近"具体锚点"的覆盖越优先。这让团队可以为不同 work item 单独定义策略而不动全局配置。

# packages/core/src/protocol.ts  L19-25
const POLICY_SCOPE_ORDER: PolicyScope[] = [
  "organization_default",            // 组织全局默认值（最低优先级）
  "adapter_surface_default",          // 适配器/平台默认
  "work_context_owner_container",     // work item 所属容器
  "work_item_override",               // 单个 work item 覆盖
  "primary_anchor_override"           // 主锚点（最高优先级）
];
AdapterMutationCompiler 是 OpenTag 的"半成品 sandbox"：当某个 mention 解析后被识别为 mutation（创建/更新 Issue、PR、回复评论），不会直接执行 API call——而是先生成 MutationIntent，经 AdapterMutationCompilerRegistry.compile() 编译成平台特定的 operation object（GitHubIssueMutationOperation / SlackBlock 等）。如果某个 adapter 没注册 compiler，编译结果 {ok: false, outcome: "unsupported"}，由 dispatcher 决定如何回写用户。这是 mutation 流水线的"中间表示"层。

dispatcher server · 1869 行的 Hono 单文件

dispatcher/src/server.ts 集中了所有 webhook 路由、admission 控制、presentation 渲染、mutation 编译、Hono HTTP 入口。这是 OpenTag 真正的运行时。

parseBody 的"只把 JSON 错映射到 400"哲学

这是 dispatcher 里第一条值得记录的设计：只把"请求体本身的语法错误"映射成 HTTP 400。其他错误（包括下游的 ZodError、SyntaxError 来自中间件）原样抛出、走 500。注释里写得很清楚："malformed JSON (SyntaxError from c.req.json()) and request-schema validation failures (ZodError from schema.parse()) are tagged as HTTPException with status 400 so the global onError handler can return them as client errors without masking unrelated internal ZodError/SyntaxError as 400s." —— 是好实践，避免把无关的内部 ZodError 误标成客户端错误。

# packages/dispatcher/src/server.ts  L41-69  (parseBody)
async function parseBody<S extends z.ZodTypeAny>(c: Context, schema: S): Promise<z.infer<S>> {
  let json: unknown;
  try {
    json = await c.req.json();
  } catch (err) {
    if (err instanceof SyntaxError) {
      throw new HTTPException(400, { res: c.json({ error: "invalid_json_body" }, 400) });
    }
    throw err;
  }

  const result = schema.safeParse(json);
  if (!result.success) {
    throw new HTTPException(400, {
      res: c.json({ error: "invalid_request_body", issues: result.error.issues }, 400)
    });
  }
  return result.data;
}

Admission Runtime · 谁能触发 executor

createAdmissionRuntime()（admission.ts 209 LOC）维护 AgentAccessProfileCheck 列表——当 webhook 事件到达时，runtime 决定这个 actor（Slack user / GitHub user / Telegram chat）是否被授权在当前 work context 上触发 executor。admission 通过后才进入 ContextPacket assembly + runner 调用。

Presentation 层 · Slack Block Kit / GitHub Comment 渲染

presentation.ts（69 LOC）+ callbacks.ts（253 LOC）——把 OpenTagRun 状态转成"用户能看到的反馈格式"：Slack 里是 Block Kit message（带 status emoji、进度条、changed files 列表），GitHub 里是 PR/Issue 评论。rendering 是双向的：用户的 mention → executor → 平台特定 message。

安全审计 · 3 mode + 17 类敏感 pattern

runner/src/security.ts（253 LOC）是 OpenTag 整套系统中对 prompt injection 最敏感的防线——因为 mention 来自外部用户，必须做严格 sandbox。

3 种安全模式

enforce（默认）—— 检测到风险直接 fail；audit—— 仍执行但记 audit log；off—— 跳过所有检测。audit 是"测试环境友好"的折衷，让 dev 阶段不被 false positive 卡住。

17 类 SENSITIVE_ENV_PATTERNS

环境变量正则：/TOKEN/、/SECRET/、/PASSWORD/、/API[_-]?KEY/、/CREDENTIAL/、/^AWS_/、/^AZURE_/、/^GCP_/、/^GOOGLE_/、/^OPENAI_/、/^ANTHROPIC_/、/^SLACK_/、/^GITHUB_TOKEN$/、/^GH_TOKEN$/、/^SSH_/ 等。这些变量会从 exec 环境里被剔除（scrubEnvironment），防止 executor 读取 secrets。

canRun 阶段：3 项前提检查

    runId: input.runId,

设计取舍 · 5 个关键决定

1. zod 3.x 作为唯一 schema 来源

所有 schema 在 core/src/schema.ts 用 zod 定义；导出时通过 zod-to-json-schema 同时产出 JSON Schema。这意味着 dispatcher 可以用 zod 做运行时校验（type-safe），同时下游 client（比如第三方 IDE 插件）可以拿 JSON Schema 做 IDE autocomplete + 静态校验。一份定义，双格式输出。

2. Hono 而非 Express

Web framework 用 Hono 而非传统 Express——Hono 是 Web Standard API，原生支持 c.req.json()、c.json()，且与 Cloudflare Workers / Deno / Bun 兼容。OpenTag 的 daemon 目前跑在 Node，但代码结构让它能在任何 Web Standard runtime 上跑。

3. better-sqlite3 + Drizzle 而不是 Prisma

本地 daemon 用本地 sqlite。Drizzle 是 type-safe SQL builder（不是 ORM），编译期校验 query 类型；better-sqlite3 是同步 API（无 callback hell）。这套组合在 Node 上是"接近零依赖"的本地持久化方案。

4. AdapterMutationCompiler · 中间表示层

GitHub / Slack / Lark 平台的 mutation 不能直接 HTTP call——要先编译成平台特定 operation object。这种"中间表示"的好处是：dispatcher 可以用统一代码路径处理 mutation，不需要为每个平台写分支。

5. ContextPointer + 7-stage assembly hooks

ContextPointer（来自 source = "slack / github / lark"）+ 7 阶段流水线 + 每阶段 hook。这是 OpenTag 协议里最复杂但最有灵活性的部分——第三方插件可以在任意阶段 hook 进去，比如"collect 阶段多收集 X 类 pointer"、"classify 阶段把所有 markdown 标 primary_evidence"。

失败模式 · 4 类已知边界

边界 1 · admission false positive：当前 admission runtime 校验"该 user 是否有权限触发"，但没有"该 user 的 mention 是否符合该 work context 的 topic scope"。理论上 Slack 里任何人都可以 @opentag fix anything，只要 admission 通过就跑——实际部署需要额外的 topic-scope policy。
边界 2 · executor 失败后状态机不完整：当 codex --version 检查通过但 run 中途 OOM/SIGKILL，OpenTagRun 状态会被标记为 partial——但 keepWorktree 默认 on_failure，worktree 会被 cleanup，可能导致后续诊断无法复原。
边界 3 · 网络策略只有 "restricted"：network: restricted 是唯一合法值，其他值（比如 none、unrestricted）会被 diagnostic warning。这意味着 OpenTag 不能跑"完全离线"或"完全开放"——只能"有限制的网络"。这是设计取舍，不是 bug。
边界 4 · ContextPointer 的事实 vs. 噪声分类不可逆：一旦 classify 阶段把某 pointer 标 sensitive_material，它永远进 background role，不再能升级为 primary_evidence。如果分类错误（误判某 GitHub PR review comment 为敏感），后续 executor 看不到这条信息。

OpenTag 的核心定位

不是"又一个 bot 框架"，而是"把现有 coding agent 接入现有协作平台"的桥。抽象层选得很精准：core 包不绑任何特定 agent / 任何特定平台，谁都能扩展；security 在 runner 层而不是 dispatcher 层——意味着你跑自己的 executor 时也能复用 security.ts。

生态意义 · "Agent 即平台公民"的协议层

对 Agent 协议化的贡献

OpenTag 的 core 包是一份schema-first 的 Agent 协议定义——所有字段都有 zod 类型，导出 JSON Schema 可以直接喂给 OpenAPI、JSON Schema-aware IDE、TypeScript codegen。这意味着：未来任意 chat platform（Discord / Teams / Matrix / 钉钉）都可以用同一份 schema 实现 OpenTag 兼容 adapter。

对 Hermes / OpenClaw 生态的呼应

EXECUTOR_HINTS 集合里包含 hermes 和 openclaw——这意味着 OpenTag 在协议层就把"我支持本地 Hermes Agent / OpenClaw"显式列出。这是一个生态联盟信号：不是"OpenTag vs Hermes"，而是"OpenTag 作为粘合层，让 Hermes 也能享受 @agent mention 的 UX"。

对企业部署的友好性

三个特性让 OpenTag 比纯云方案更适合企业：① admission runtime + scope policy——可以控制"哪些 channel / 哪些 user 可以触发"；② git worktree 隔离——变更不污染主分支；③ audit mode——可观察性而不破坏执行。本地 daemon 部署也让审计/合规部门更容易接受。

对效铭的提示：OpenTag 的架构是"协议 → dispatcher → runner → executor"四层，最容易复用的是 @opentag/core——如果哪天你想做一个新的"agent 协作平台"，先看 core 包能不能复用，再决定要不要 fork dispatcher。
