§ 01 · ARCHITECTURE

协议与调度拓扑

架构可以拆成三段：输入契约、核心处理、输出/评分/写入。每段都有独立文件承接，而不是把逻辑堆在 README 示例里。

▸系统拓扑

graph TD A[Platform or dataset event] --> B[opentag contract layer] B --> C[Normalization and parsing] C --> D[Execution or evaluation loop] D --> E[Result, score, or local memory] C --> F[Validation and edge handling]

▸模块清单

协议入口
事件、上下文、权限和 mutation intent 先归一成可校验契约。
调度核心
Dispatcher/runner 只交换 run、progress、result，不绑定具体平台 UI。
验证层
Parser、schema 和单测围绕失败输入设计，避免无声漂移。

▸已知边界 / 失败模式

  • 仓库发布节奏快，页面引用的行号必须以后续 clone 为准重新校验。
  • 外部平台、模型 API 或本地 CLI 的错误不会总是同构，需要保留原始错误。

§ 05 · HIGHLIGHTS

值得保留的设计

契约清晰
核心边界被拆到独立模块，读者可以直接从行号回溯。
失败可见
解析、评分、路径和权限错误大多被显式编码，而不是吞掉。
局部可替换
平台、模型或摘要后端通过配置/接口切换。
测试有抓手
单测围绕 parser、security、config 或 runner 这样的真实风险点。
