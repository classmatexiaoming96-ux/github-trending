14## Phase 1 — Shape the idea into a spec
15
16Turn what the guardian said into a short, plain-language spec they can read and
17sign off on. The spec is the thing they approve, so write it for a non-technical
18reader — what the automation *does*, not how it's coded. Use this shape:
19
20> **Trigger** — what kicks it off (a schedule, an event, a "run now").
21> **Steps** — the ordered things it does, one short verb phrase each
22> ("fetch my unread emails", "summarize them", "post the digest to my chat").
23> **Decisions** — any branch ("if the total is over $5k, escalate; otherwise file
24> it"), stated as plain conditions.
25> **Per-item work** — anything done "for each" of a list ("for each ticket, rate
26> its severity").
27> **Delivers** — the final step that sends, posts, saves, or shows the result.
28
29Hold these disciplines while you shape it — they decide whether the spec is real:
30
31- **Ask the guardian for facts only they can supply; never invent them.** A
32  threshold amount, a recipient, a channel, which account, which event fires the
33  trigger — a made-up "$5,000" looks authoritative and gets approved by accident.
34  When a fact like this is missing, ask for it in your reply rather than guessing.
35- **Resolve design questions in conversation, not in the spec.** Anything that
36  changes the *shape* — whether to branch, what to do per item — gets settled with
37  the guardian before you present the spec, not parked as an open question in it.
38- **Every workflow must deliver.** A spec that only fetches and computes, with no
39  step that sends/posts/saves/shows a result, has no destination and is never
40  finished. If the guardian didn't say where the result goes, that's a fact to ask
41  for (see above).
42- **Don't let vague quantifiers pass.** "the top labs", "the latest news", "key
43  themes", "top outlets" each hide a fact — how many, which sources, what time
44  window. If it changes what the automation does, pin it down with the guardian.
45- **Keep it statically structured.** The full space of what it does must be
46  knowable before it runs: ordered steps, parallel work, a decision, or bounded
47  per-item fan-out. No "keep polling until…", no unbounded loops.
48
49Keep the spec itself conversational and free of technical artifacts — no JSON, no
50flow chart, no node/combinator vocabulary. Talk about what it will *do*.
51
52## Phase 2 — Get approval
53
54Present the spec and ask the guardian to approve it or tell you what to change.
55Make the ask explicit ("Want me to build this, or change anything first?"). If
56they ask for a change, revise the spec and ask again. Build **only** after a clear
57yes — don't start scaffolding on a maybe.
58
59## Phase 3 — Build it
60
61On approval, build the workflow into a new, runnable Rome app. **Load the
62`coding:workflow_creation` skill and follow it end to end** — it owns the real work:
63deriving the control flow, scaffolding the `workflow` template, authoring
64`src/workflow/definition.ts` in plain TypeScript (`await`/`if`/`for`/`Promise.all`),
65the `system:summon` discipline for generative steps, the `connector:connector_proxy` discipline for
66SaaS calls, the `ctx.dryRun` guard on every write, the display envelope, the web
67surface, and the install. Translate the approved spec into its control flow
68faithfully — don't redesign the automation while coding it.
