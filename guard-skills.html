Three Trigger Modes

Every guard skill (clean-code-guard, test-guard, docs-guard, wp-guard, woo-guard) operates in one of three modes. The user's request determines which mode activates.

Guard-Pass

Recommended — Reactive Review

Run after code has been generated, edited, refactored, or fixed. Check the diff or target files against all Always-applied imperatives before presenting, committing, or merging.

  • After a coding agent writes or edits implementation
  • After a refactor — preserve behavior exactly
  • Before a PR is presented or a commit is made

Trigger phrases: "review this PR", "is this safe to merge?", "check this diff", "should I commit this?"

Live

Explicit — Constrained Writing

When the user explicitly invokes the guard before a risky code edit, apply the same imperatives while writing, then run the Self-check before delivery before showing the result.

  • User says "use clean-code-guard while implementing this"
  • Risky structural changes (extraction, abstraction, rewrite)
  • When you want the constraint active during generation

Trigger phrases: "use $clean-code-guard while you write", "implement this endpoint using clean-code-guard"

Review

Triggered — Structured Audit

When the user asks to review, audit, critique, or rate code, walk the full Review-Mode Checklist against the target files and produce a structured findings report. Do not edit code unless asked.

  • User asks "review this PR" or "audit this code"
  • Code-review for correctness — behavior changes in scope
  • Structured output with severity ratings (Critical / Important / Nit)

Trigger phrases: "review", "audit", "critique", "rate this code", "assess this"

Decision tree: Did code get written or changed → guard-pass. Did you invoke before writing → live. Did the user ask to review/audit → review. Never blend modes: a review does not edit; a guard-pass does not produce a findings report.

14 Systematic LLM Failure Modes

These are the highest-leverage checks. Eight of the 14 trace to one root cause: the model is biased toward emitting more code, more parameters, more guards, more abstractions — anything but the minimum required by the spec. Walk these before every delivery.

# Pattern Rule (Self-Check) Source
1 Catch-all error handling that swallows failures Catch only the specific error type you can recover from. Never use broad catch any or return null/empty success from a handler unless the contract documents it. Karpathy; field reports on LLM error suppression
2 Defensive guards for impossible cases Do not add null checks or runtime type checks for values whose type annotation or caller contract already excludes that case. Trust the contract. arXiv 2409.19182
3 Premature abstraction Do not introduce an interface, abstract class, factory, registry, strategy, or plugin pattern unless two or more concrete implementations exist today. One implementation = inline it. Fowler, "Patterns for Reducing Friction"
4 Comment pollution Comments explain why, never what. Strip restating-code comments, step-number scaffolding, and docstrings that paraphrase the signature. HN #43929768; arXiv 2402.13013
5 Code duplication instead of reuse Before writing a block of ≥5 lines, search the codebase for a similar existing function. Duplicated knowledge is a violation; duplicated text matching existing helpers is also a violation. GitClear 2025 — 211M-LoC, 8× growth 2021–2024
6 Hallucinated APIs and packages Every import and external API call must be verified against the actual installed version. Read the package, check the lockfile, or import and inspect. Do not call a method based on what "should" exist. USENIX Security '25 — 16 models, 19.6% avg hallucination rate
7 Generic, intent-less naming Ban data, result, item, temp, value, obj, info, helper, manager, handle_*, process_*, do_* unless qualified. Names must reveal intent. arXiv 2512.01141; arXiv 2510.03178
8 Long functions doing many things A function does one thing. Hard caps: ≤50 lines, ≤4 parameters, cyclomatic complexity ≤8. If the prompt asked for N things, produce N functions and a small composer. GitClear 2025 — file size 142→267 LoC; arXiv 2512.11922
9 Parameter explosion When a function reaches 5 parameters, stop and introduce a typed request/config object (record, struct, DTO). Do not keep adding positional args. arXiv 2304.10778; Fowler's overeagerness pattern
10 Inconsistency with surrounding code Before writing in a file, read the file and at least one neighbor. Match casing, import style, error handling pattern, and logging style. Reuse existing utilities. Pullflow "The Context Illusion"; Honeycomb field reports
11 Dead code, unused imports, half-implementations Run a linter or grep pass for unused imports, unused symbols, unreachable branches, and "just in case" exports. Remove them before delivery. arXiv 2411.01414; GitClear "added-code dominates deleted"
12 Declares success — mock fallbacks in production code Never return hardcoded "success" values or fixture data from a function the spec says should perform real work. If you cannot implement, fail explicitly and say what is missing. Fowler "Patterns for Reducing Friction"; Claude Code #6984
13 Plausible-but-wrong code For any boundary, range, off-by-one, or null-semantic question, write the case enumeration in a comment first. Never copy a similar function and adapt — re-derive from the spec. arXiv 2411.01414; Katanaquant "Plausible Code"
14 YAGNI violations — speculative configurability No optional parameter, config flag, env var, or feature toggle without a present-day caller. If you find yourself adding enable_*, use_*, or *_mode, delete it and ship the concrete behavior. Fowler "YAGNI"; HN defensive-code thread
Cross-cutting root cause: Eight of the 14 failure modes (1, 2, 3, 9, 12, 14, plus pieces of 8 and 11) come from one bias — the model is rewarded for emitting more code. The cure is restraint. Before writing each line, ask: does the spec require this, today? If no, do not write it.

23 Always-Applied Imperatives

These rules apply to every code change in guard-pass and live modes. They are imperative, not suggestions.

1. Names reveal intent. Never use data, result, item, temp, value, obj, info, helper, manager, utils, or handle_*/process_*/do_* without a qualifier. A name must answer why it exists and what it does. (Clean Code Ch. 2)
2. Functions stay small. Target ≤20 lines, one level of abstraction, one thing. If you can extract a function with a name that doesn't restate the body, the parent was doing more than one thing. (Clean Code Ch. 3)
3. Four arguments is the hard ceiling. At five, stop and introduce a request/config object (record, struct, DTO). Never use boolean flag arguments — split into two functions instead.
4. No output arguments. A function either returns a value (query) or has a side effect (command). Never both. Command names use verbs; query names use nouns or getter-style names. (CQS)
5. Comments explain why, never what. Delete any comment that paraphrases the line below it. Delete step-number scaffolding. Delete commented-out code — version control exists. (Clean Code Ch. 4)
6. Match the file's existing style. Read the file you're editing and at least one neighbor before writing. Mirror casing, import order, error handling, logging, and HTTP/DB client choices. Do not introduce a second pattern.
7. One actor per module. A class should be answerable to one stakeholder group (Accounting, Auth, Reporting). If two unrelated subsystems both reach into the same class, split it. (SRP, Uncle Bob 2014)
8. Extension via new code, not edits. If adding a new variant requires another type-tag branch in an existing function, refactor to a registry, strategy, or polymorphic dispatch first. (OCP)
9. No subclass refuses its parent's contract. Never override a method to signal "not implemented" or "unsupported operation." Never strengthen preconditions or weaken postconditions in an override. If you need to do that, the inheritance is wrong. (LSP)
10. Abstractions live with the client, not the implementation. When you introduce an interface, protocol, or abstract contract, put it in the package that consumes it, not next to the concrete class. (DIP)
11. Delete duplicated knowledge, not duplicated text. Two functions that look alike but encode different rules are not a DRY violation. One rule expressed in code + docs + schema is. (Pragmatic Programmer, "DRY")
12. The wrong abstraction is worse than duplication. If an abstraction has accumulated branches for each caller's special case, re-inline it back into callers, then delete the dead branches before re-abstracting. (Sandi Metz, "The Wrong Abstraction")
13. Complexity ceiling: cyclomatic ≤10, nesting depth ≤5. Refactor before exceeding. (McCabe 1976)
14. No speculative anything. No optional parameter, config flag, env var, feature toggle, interface, factory, or base class without a present-day caller. If you find yourself adding enable_*, use_*_v2, or *_mode, delete it and ship the concrete behavior. (Fowler, "YAGNI")
15. Never swallow errors with broad catch-all handling. Catch only the specific error type you can recover from. If you cannot recover, let the error propagate. Returning null/none/empty success from a catch handler is forbidden unless the function contract documents that behavior. (Karpathy)
16. No defensive guards for impossible cases. Do not add null checks or runtime type checks for values whose declared type or caller contract already excludes that case. Trust the contract. (arXiv 2409.19182)
17. Verify every import and external call. Before calling a method on a library, confirm it exists in the version installed (read the package, check the lockfile, or import and inspect). Do not generate code based on what the API "should" look like. (USENIX Security '25)
18. No hardcoded "success" returns or mock fixtures in production code. Never return {"status": "ok", ...} or canned data from a function whose spec says it does real work. If you cannot implement, fail explicitly with the language's unimplemented or unsupported-operation mechanism and say so. Never disable, skip, or weaken a test to make it pass. (Fowler, Claude Code #6984)
19. Re-derive, do not copy from similar. When tempted to copy a function and modify it, stop. Re-derive from the spec. Off-by-one and wrong-null-semantic bugs almost always enter through copy-from-similar. (arXiv 2411.01414)
20. Enumerate boundary cases before writing them. For any range, off-by-one, null/empty/one/many, even/odd, or unicode/byte boundary, write the case list in a comment first. Cover each case in code before moving on.
21. Strip dead code before delivery. Run a linter or grep pass for unused imports, unused symbols, unreachable branches, and "just in case" exports. Remove them. A function that nothing calls today does not get to live for "someday."
22. Read before write. Before writing in an unfamiliar repo, read the file you'll edit, one neighbor, and any project rules file (CLAUDE.md, AGENTS.md, README's "conventions" section). Use the project's existing helpers, error types, and logging.
23. Preserve observable behavior when refactoring. Same inputs produce the same outputs, same exceptions raised, same side effects, same ordering guarantees. If you spot a bug while refactoring, flag it separately and ask before changing it. Refactoring is defined as a change to internal structure to make it easier to understand without changing observable behavior (Fowler, Refactoring). Bug fixes and refactors are two operations — never bundle them.

8-Step Self-Check Before Delivery

Run this checklist before showing the user any code you wrote or edited. If you cannot answer yes to every step, fix before shipping.

Walk imperatives 1–23 against your diff. Fix every violation.
Every rule in the Always-Applied Imperatives section applies to every change. Scan the full diff and confirm none of the 23 are violated.
For new functions, count: lines ≤ 20? params ≤ 4? complexity feels ≤ 10? names reveal intent?
Apply the hard caps from imperatives 1–3. A function that exceeds these limits almost certainly does more than one thing or carries a hidden abstraction.
For new comments, ask: does this explain why? If it explains what, delete it.
Imperative 5 is the filter. If a comment paraphrases the line below it, it adds noise, not signal. If a step-number scaffold remains, remove it.
For new error handling: is the caught error type specific? Does the handler do something other than silently return?
Imperatives 15 and 18. A catch handler that returns null or empty success without a documented recovery path is a failure. Catch only what you can act on.
For new abstractions (interface, factory, base class, registry): is there a second concrete user today? If no, inline it.
Imperative 3 and 12. An abstraction with a single implementation is premature. An abstraction with per-caller branches accumulating is the wrong abstraction.
Did you read the file you edited and at least one neighbor? Did your style match?
Imperative 6 and 22. Style inconsistency is one of the top three findings in LLM code reviews. Read the file before writing in it.
Is there any hardcoded "ok" return or fixture data? If yes, replace with real implementation or an explicit unimplemented/unsupported-operation failure.
Imperative 18. This is the most dangerous AI pattern — it makes the code appear to work while shipping fiction. It must be caught before delivery.
If this is a refactor: did you change observable behavior? If yes, you bundled a bug fix — split it out and ask the user.
Imperative 23. Refactoring and bug fixing are two separate operations. Combining them in a single diff means neither can be reviewed cleanly.

Quick-Reference Bad / Good Examples

The most common failure patterns with concrete before/after.

Failure Mode 1 — Catch-all error swallowing

# BAD — a database outage is now indistinguishable from "user has no email"
getEmail(userId):
  attempt:
    user = userStore.get(userId)
    return user.email
  catch anyError:
    return null
# GOOD — storage errors propagate; null only means the user has no email
getEmail(userId):
  user = userStore.get(userId)  # errors propagate
  return user.email

Failure Mode 2 — Defensive guards for impossible cases

# BAD — the contract says orderItems is a collection; none of these guards can fire
total(orderItems):
  if orderItems is null: return 0
  if orderItems is not a collection: return 0
  return sum(order.amount for each non-null order in orderItems)
# GOOD — trust the contract
total(orderItems):
  return sum(order.amount for each order in orderItems)

Failure Mode 3 — Premature abstraction

# BAD — exactly one payment processor; the abstract interface and factory are pure ceremony
PaymentProcessor interface
  charge(amount)
CardPaymentProcessor implements PaymentProcessor
  charge(amount):
    return paymentProvider.createCharge(amount).id
PaymentProcessorFactory
  create():
    return new CardPaymentProcessor()
# GOOD — one concrete function, no ceremony
charge(amount):
  return paymentProvider.createCharge(amount).id

Failure Mode 7 — Generic, intent-less naming

# BAD — none of these names reveal intent
processData(data):
  result = []
  for item in data:
    temp = item.value * 2
    result.add(temp)
  return result
# GOOD — names answer why the function exists and what it does
doublePrices(orders):
  return orders.map(order -> order.priceCents * 2)

Failure Mode 9 — Parameter explosion

# BAD — should be a typed config object
sendEmail(to, subject, body, retry=true, backoff="exp",
          html=false, fromAddress=null, encoding="utf-8",
          internal=false, verbose=false)
# GOOD — a typed request object scales cleanly
EmailRequest
  to
  subject
  body
  html = false

sendEmail(request: EmailRequest)

Failure Mode 12 — Declares success with mock fallback

# BAD — shipped as the implementation, function body is fiction
getUserBalance(userId):
  return 1000  # TODO: actual provider call
# GOOD — explicit failure, clearly states what is missing
getUserBalance(userId):
  raise NotImplemented("Wire to billing.getBalance() after auth is available")

Failure Mode 13 — Plausible-but-wrong (copy-from-similar)

# BAD — off-by-one for odd-length arrays
median = (values[values.length / 2] + values[values.length / 2 + 1]) / 2

# BAD — silently drops items[0]
for index from 1 to items.length - 1:
  ...
# GOOD — case enumeration first, then code
# cases: empty / one / even / odd
median(values):
  sorted = values.sort()
  mid = sorted.length / 2
  return sorted.length % 2 == 0
    ? (sorted[mid-1] + sorted[mid]) / 2
    : sorted[mid]
