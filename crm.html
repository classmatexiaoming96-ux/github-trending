crm agentic-first CRM

trycompai/crm 把 CRM 设计成 Agent 的工作台：API 只入队事实，Agent 按预算研究和记录，前端 Agent Tab 负责把可追踪会话交给销售代表。

§ 00 · OVERVIEW

它解决什么，凭什么值得拆

这个项目最有意思的地方是产品定义倒置：CRM 不是给销售代表手填字段的数据库，而是 Agent 用来保存观察、建议和后续动作的系统。packages/db/prisma/schema.prisma:312 的 AgentTask、packages/db/prisma/schema.prisma:339 的 AgentEvent 和 packages/db/prisma/schema.prisma:353 的 AgentConversation 把“后台研究”和“前台对话”都变成一等数据。

源码层面它分得很清楚：apps/api/src/agent/agent-trigger.service.ts:146 负责把业务事件写成任务，apps/agent/agent/lib/tasks.ts:28 负责可并发领取，apps/agent/agent/lib/dispatch.ts:132 把直接任务和研究任务合并成一次 drain，apps/agent/agent/tools/record_fact.ts:8 则强制 Agent 带证据写事实。这个边界让它比 README 里的“agentic-first”更可信。

▸核心数据

架构模式
Bun/Turborepo monorepo，Next.js 前端 + NestJS/tRPC API + Eve durable agent + Prisma/Postgres。
核心抽象
AgentTask 是工作入口，Evidence/FactBand 是事实门禁，AgentConversation 是用户可回看的会话索引。
性能/可靠性
数据库租约、优先级、最大重试、过期回收和 fire-and-forget poke 避免把在线请求绑死在 Agent 可用性上。
下游依赖
Eve、Vercel Sandbox、Vercel AI Gateway、Prisma、Better Auth、tRPC、Context.dev、Google sync。

§ 06 · RISKS

技术亮点之外，别忽略这些

第一，apps/api/src/agent/agent-trigger.service.ts:195 的 poke 是 fire-and-forget，产品上合理，但运维必须能区分“poke 没打到”和“cron 没跑”。第二，apps/agent/agent/sandbox/sandbox.ts:5 的 deny-all 很好，但所有真正外部访问都转移到工具和 provider 侧，需要审计工具实现。

第三，apps/agent/agent/lib/evidence.ts:97 的阈值是业务判断，不是数学真理；上线后应该用 dismissed/proposed/applied 的反馈重新校准。第四，apps/app/lib/agent-bridge.ts:4 的 120 秒 token TTL 对安全友好，但长会话恢复和多标签行为要继续观察。

▸队列契约落在共享包

主线实现虽然在 Agent app 里，持久契约要回到 packages/db/src/agent-tasks.ts:1 看类型入口；packages/db/src/agent-tasks.ts:14 把 direct lane 的 kind 列出来，packages/db/src/agent-tasks.ts:22 再把队列 subject 约束为 company、contact 或 workspace。这个共享包是 API 入队、调度器领取和测试断言共同依赖的最小事实层。

▸数据库客户端是系统边界

packages/db/src/client.ts:55 暴露的 prisma 客户端让 API、Agent 与前端后台逻辑共享同一条访问路径；分析 crm 时不能只看会话代码，因为 queue claim、fact transaction 和 conversation persistence 都要通过这层客户端进入数据库。

▸JSON 类型避免证据漂移

packages/db/src/json.ts:1 到 packages/db/src/json.ts:13 定义了可复用 JSON 值类型，适合承载 evidence、metadata、outcome 这类跨模块字段。它让 Agent 写入的结构化证据不会退化成任意字符串，也方便后续做审核、回放和 UI 渲染。

▸设置读取影响运行时行为

packages/db/src/settings.ts:16 和 packages/db/src/settings.ts:54 表明运行时配置不是散落在组件里的常量；当 Agent 调度频率、认证、工作区能力或外部 provider 配置变化时，这类设置入口会成为排查线上行为差异的第一站。

▸外部读取要有安全包装

packages/db/src/safe-fetch.ts:8 到 packages/db/src/safe-fetch.ts:37 给出了安全抓取的辅助边界。CRM 的 sandbox 是 deny-all，但真正的数据补全仍可能依赖受控工具，因此这类安全包装决定了 Agent 能否在不放大 SSRF 和任意请求风险的前提下完成研究。

▸对象存储承接可见资产

packages/db/src/blob.ts:25 与 packages/db/src/blob.ts:49 解释了头像、logo 或研究附件这类二进制结果应该怎样离开 Agent 流程并进入可服务的存储层。对 CRM 用户而言，可见资产的稳定展示和文字事实一样重要。

▸工作区边界决定多租户安全

packages/db/src/workspace.ts:54 和 packages/db/src/workspace.ts:73 是多租户场景下必须同时阅读的边界。Agent 任务携带 workspaceId，只要工作区解析或成员关系判断出错，研究结果就可能写到错误客户空间，这是比单次生成失败更严重的问题。

▸任务状态需要可恢复

packages/db/src/agent-tasks.ts:18 与 packages/db/src/agent-tasks.ts:31 对应任务 subject 和 kind 的类型边界；它们让调度器可以在进程重启、租约过期、session 回调延迟后继续解释一条任务应当怎样恢复，而不是靠临时内存猜测。

▸索引页选择的是架构信号

packages/db/src/agent-tasks.ts:22、packages/db/src/client.ts:61 和 packages/db/src/settings.ts:34 合在一起说明，trycompai/crm 的热门价值不只是“CRM 加聊天框”。它把队列、数据库、配置和前端会话做成一条可审计链路，所以值得作为本期 Agentic CRM 项目拆解。

亮点
队列租约、证据账本、deny-all sandbox 和持久会话共同把 Agent 做成业务系统，而不是聊天外挂。
风险
能力边界分散在 API、Eve、sandbox、工具和前端缓存之间，后续维护要靠文档和测试持续约束。
