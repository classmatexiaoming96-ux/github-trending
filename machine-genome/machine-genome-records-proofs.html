记录、签名与血缘授权 深度解析

这一页聚焦 MGS 如何从 CLI 输入生成 unsigned genesis，如何把 Data Integrity proof 加到 canonical JSON 上，以及如何让 parent 对 child lineage 做不循环的授权。

§ 00 · IMPORT CHAIN

导入链与契约

▸CLI 是协议对象的最短入口

入口 cmd/mgs/main.go:37 把所有命令统一分发，cmd/mgs/main.go:43、cmd/mgs/main.go:45、cmd/mgs/main.go:47、cmd/mgs/main.go:49、cmd/mgs/main.go:51 和 cmd/mgs/main.go:57 分别暴露 keygen、init-genesis、sign、authorize-edge、gene 和 verify。这个分发层看似普通，但它规定了用户能进入协议的路径：先生成 key，再构造 genesis，再签名，再验证或登记。后续 record/proof 逻辑都不直接依赖 HTTP，因此 CLI 和 registry 可以共享同一组库函数。

§ 02 · KEY FLOW

关键流程

run init-genesis -> load controller key -> build GenesisRecord -> ValidateGenesis(requireProof=false) -> sign -> SignRecord checks recordType -> SignDocument adds eddsa-jcs-2022 proof -> VerifyGenesis recomputes canonical hash -> Gene returns content-addressed identity

这条流程可以从 cmd/mgs/main.go:123、cmd/mgs/main.go:140、cmd/mgs/main.go:151、cmd/mgs/main.go:172、mgs/record.go:171、mgs/proof.go:78、mgs/record.go:152 和 mgs/record.go:168 连起来看。测试 cmd/mgs/main_test.go:50 到 cmd/mgs/main_test.go:75 对应这条路径，确保真实命令能产出以 zQm 开头的 Gene。

§ 03 · EDGE CASES

边界 / 失败模式

  • mgs/record.go:127 对 unresolved parentage 有严格组合约束，防止一个 edge 同时声明 unresolved 又夹带 parentGene 或 authorizationProof。
  • mgs/proof.go:90 会拒绝已经带 proof 的文档，避免签名对象被重复包装。
  • mgs/proof.go:145 到 mgs/proof.go:151 要求 proof @context 与 document @context 一致，减少上下文偷换。
  • mgs/lineage.go:176 到 mgs/lineage.go:185 要求授权 proof signer 是 parent controller 且使用 parent genesis key。
  • cmd/mgs/main_test.go:79 到 cmd/mgs/main_test.go:86 还测试未知命令必须失败并输出 usage，避免 CLI 静默吞错。
读者应该带走的点

Machine Genome 的 proof 不是“签一个 JSON 文件”这么简单，而是把 canonicalization、proof config、DID method 和 record-specific controller 关系绑在一起。

仍需补齐的点

当前 profile 偏向 did:key 和 genesis key，跨组织 key rotation 与更多 DID method 支持还需要后续治理和 resolver 扩展。
