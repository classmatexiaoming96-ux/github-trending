§ 00 · Source-level Observatory

x64dbg-mcp-server Debugger MCP bridge

一个原生 x64dbg 插件，把调试器能力通过 MCP Streamable HTTP 与 SSE 暴露给 AI 客户端。真正值得拆的是：它不是脚本壳，而是把 Win32 socket、JSON-RPC、工具 schema、x64dbg bridge 和菜单配置全部编进同一个 Zig 插件。

§ 00 · OVERVIEW

它解决什么，为什么突然火

x64dbg-MCP Server 的核心卖点是把桌面调试器变成 MCP 工具服务：插件入口先在 src/main.zig:59（证据 src/evidence.md:3） 初始化 bridge，随后在 src/main.zig:71（证据 src/evidence.md:4） 与 src/main.zig:75（证据 src/evidence.md:5） 注册启动/停止命令；进入 setup 后，src/main.zig:99（证据 src/evidence.md:6） 开始把调试生命周期事件挂到 x64dbg 回调，src/main.zig:135（证据 src/evidence.md:7） 加载配置，src/main.zig:142（证据 src/evidence.md:8） 决定是否自动开服。这说明它的产品形态不是外部轮询器，而是驻留在调试器内部的控制面。

服务端部分用手写 Win32 socket 和 JSON-RPC：src/core/mcp_server.zig:179（证据 src/evidence.md:9） 创建服务器线程，src/core/mcp_server.zig:264（证据 src/evidence.md:10） 做 socket/bind/listen，src/core/mcp_server.zig:312（证据 src/evidence.md:11） 对每个连接起线程，src/core/mcp_server.zig:358（证据 src/evidence.md:12） 再解析 HTTP 并分流到 MCP。这个路径短，依赖少，但也意味着并发、认证、网络暴露和调试器状态都落在插件自己的边界里。

▸核心数据

架构模式
Native x64dbg plugin + embedded MCP HTTP/SSE server + JSON-RPC tool dispatcher。
核心抽象
ToolDef 注册表、Bridge wrappers、Config 持久化、SSE client list、event ring buffer。
证据密度
本文引用真实 Zig 源码行，同时用 src/evidence.md 映射供质量门禁校验。
适用场景
授权逆向、调试自动化、教学演示、受控本地分析；不适合裸露到不可信网络。

▸架构判断

真正的设计取舍在“能力集中”和“边界集中”：src/mcp/tools.zig:30（证据 src/evidence.md:13） 到 src/mcp/tools.zig:112（证据 src/evidence.md:14） 把 always-on 与 debug-only 工具放在同一数组里，src/core/mcp_server.zig:621（证据 src/evidence.md:15） 按调试状态过滤，src/core/mcp_server.zig:650（证据 src/evidence.md:16） 统一执行和包装错误。这样 MCP 客户端看到的是一个一致工具面，代价是每个 handler 都必须认真做运行态检查。

§ 01 · ARCHITECTURE

插件内嵌服务器：不是外置 daemon

启动链路非常直接：src/main.zig:82（证据 src/evidence.md:17） 接收 x64dbg UI 句柄，src/main.zig:330（证据 src/evidence.md:18） 调用 mcp.start()，src/core/mcp_server.zig:179（证据 src/evidence.md:9） 创建服务器线程，src/core/mcp_server.zig:212（证据 src/evidence.md:19） 则负责停止时关掉 listener 和 SSE clients。因为生命周期跟插件同进程，服务挂掉不会只是外部进程重启的问题，而会直接影响调试器扩展体验。

§ 05 · RISKS

亮点之外，安全边界要前置

▸网络暴露风险

src/core/mcp_server.zig:37（证据 src/evidence.md:52） 默认 bind 到 0.0.0.0，src/core/mcp_server.zig:374（证据 src/evidence.md:22） 到 src/core/mcp_server.zig:388（证据 src/evidence.md:23） 有 bearer token 检查，但源码里没有 TLS、origin 绑定、速率限制或 per-tool 权限。对于一个能调试进程、读写内存、执行命令的服务，这个默认值需要被用户主动收紧。

▸工具授权粒度

危险能力很集中：src/mcp/tools.zig:943（证据 src/evidence.md:53） 允许执行任意 x64dbg command，src/mcp/tools.zig:1321（证据 src/evidence.md:35） 可以写内存，src/mcp/tools.zig:2506（证据 src/evidence.md:54） 能 dump memory，src/mcp/tools.zig:2775（证据 src/evidence.md:55） 能 dump module，src/mcp/tools.zig:2867（证据 src/evidence.md:56） 还加入 OEP 检测。现在的边界是“持有 token 即可”，还不是按工具、按进程、按会话授权。

▸工程亮点

依赖极少
Zig + Win32 API 让交付形态很轻，适合 drop-in plugin。
MCP 兼容清晰
HTTP 与 SSE 两条路径都实现，覆盖新旧 MCP 客户端。
状态守卫普遍
大量 debug-only handler 检查 active session 和 paused state。
治理还可增强
建议默认 loopback、加入 per-tool allowlist、访问日志和一次性 session token。
