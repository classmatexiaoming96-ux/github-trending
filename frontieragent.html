§ 00 · OVERVIEW

它解决什么，凭什么值得拆

FrontierAgent 的主线不是把一个聊天机器人套上终端皮肤，而是把长程研究和文件工作拆成运行时、工作流、工具、观察者和 UI。入口层在 sources/frontieragent/apodex/task_runner.py:427 明确说原生 workflow 需要注册 AgentBus、workflow roles 和完整工具表；这意味着 Agent Team 不是 generic ReAct 假装并行，而是另一条真正的 pipeline。

源码里最值得关注的是它对失败的态度：任务派发有深度和并发 guard sources/frontieragent/frontier_agent/components/agent_bus/bus.py:431，报告收集会区分 no_work_queued、running、all_collected sources/frontieragent/plugins/tools/collect_reports.py:139，审批层在运行前展示 diff 或 command sources/frontieragent/apodex/observers.py:469，trace observer 逐行写 JSONL sources/frontieragent/apodex/trace.py:30。这是一套偏生产运行的 agent harness。

▸核心数据

架构模式
分层 runtime：`apodex/` 负责 CLI/TUI/session，`workflows/` 负责 ReAct 与 Agent Team，`frontier_agent/components/agent_bus/` 负责异步 sub-agent bus，`plugins/tools/` 负责工具契约与沙箱能力。
核心抽象
核心抽象是 AgentBus + SubAgentSession + workflow profile。AgentBus 保存 jobs、sessions、spawn guard、event sink 和共享 artifact pool；profile 决定 reporter、模型、工具和 workflow 绑定。
性能/精度数据
README 展示 Apodex 1.1 benchmark 图，源码侧更硬的数字是守护逻辑中的经验值：过度复用 sub-agent session 会让模型被旧结论锚定，所以单 session 上限固定为 5。
下游依赖
下游是终端 TUI、Docker/native sandbox、SGLang/local endpoint、FrontierSearchBench/FrontierChallenge，以及可复用的 benchmark runner。

§ 02 · CORE MODULES

Agent Team 与工具契约

▸Profile loader 是工作流配置的第一道门

Agent Team 不把所有参数硬编码进 prompt，而是通过 profile loader 装载 YAML 或 inline profile，再做 env-var resolution、provider credential 注入、overrides deep merge 和 blacklist merge。sources/frontieragent/workflows/agent_team/profile.py:132 到 sources/frontieragent/workflows/agent_team/profile.py:178 显示了这个顺序；sources/frontieragent/workflows/agent_team/profile.py:88 的 deep_merge_overrides 说明 overrides 不会污染 base profile。

src/workflows/agent_team/profile.py · L88-120Python
88def deep_merge_overrides(
89    base: dict[str, Any], overrides: dict[str, Any],
90) -> dict[str, Any]:
91    """Deep-merge ``overrides`` onto ``base`` without mutating either.
92
93    Semantics chosen to match SDK caller intent (override one nested
94    knob, leave siblings alone):
95
96    - Nested dicts merge recursively (sibling keys preserved).
97    - Lists are replaced wholesale — partial list merging is almost
98      never what callers want (e.g. ``fallback_api_keys: [new_key]``
99      should *replace* the existing key list, not append).
100    - ``None`` in the override **removes** the key, so callers can
101      disable a defaulted-on feature.
102    - Scalar override replacing a dict in base wins — caller asked
103      for that shape, however unusual.
104    """
105    if not overrides:
106        # Returning a deep copy preserves the contract that the caller
107        # can mutate the result without leaking back into ``base``.
108        return _deep_copy(base)
109
110    out: dict[str, Any] = _deep_copy(base)
111    for key, value in overrides.items():
112        if value is None:
113            out.pop(key, None)
114            continue
115        base_value = out.get(key)
116        if isinstance(base_value, dict) and isinstance(value, dict):
117            out[key] = deep_merge_overrides(base_value, value)
118        else:
119            out[key] = _deep_copy(value)
120    return out

§ 03 · KEY FLOW

任务派发、收集与恢复

任务流的关键在两侧：派发时要限制深度、预算和 session 污染；收集时要避免无意义轮询并保留 partial evidence。sources/frontieragent/frontier_agent/components/agent_bus/bus.py:431 是 submit 非阻塞入口，sources/frontieragent/plugins/tools/collect_reports.py:130 是模型可见 fan-in 入口，sources/frontieragent/frontier_agent/components/agent_bus/fan_in.py:147 定义报告状态分类。

▸AgentBus 派发路径

assign_task │ validates assignment / publish manifest ▼ AgentBus.submit_task_to_session │ session boundary + job metadata ▼ _run_and_finalize │ SpawnGuard + runtime observers ▼ SubAgentResult queued for collect_reports

▸报告收集与状态短路

collect_reports(timeout) ├─ drain ready reports ├─ classify no_subagents / no_work_queued / all_collected ├─ wait first completion when running └─ render

▸模型可见 fan-in 契约

collect_reports 的 docstring 本身就是工具契约。它在 sources/frontieragent/plugins/tools/collect_reports.py:130 进入工具定义，随后把“已有结果立即 drain、没有任务时不要轮询、运行中等待首个完成、partial evidence 继续可用”写成模型可读规则。

§ 06 · RISKS & GAPS

技术亮点之外，别忽略这些

源码成熟度不错，但这是 2026-08-22 新仓库，风险主要在生态稳定性和运行面复杂度。下面这些不是否定项目，而是使用前需要明确的工程边界。

新项目版本变化快
最近 commit 是 2026-08-26，公开 API 与 profile schema 可能继续变化。依赖 sources/frontieragent/workflows/agent_team/profile.py:27 这类 alias 兼容层时要锁版本。
权限模型仍需外部制度
代码能在 sources/frontieragent/apodex/observers.py:498 请求确认，但团队仍要规定哪些命令能 remember、哪些必须人工复核。
并行不是免费
SpawnGuard 和 session cap 降低失控风险，但多 agent 会放大 token、网络和验证成本；sources/frontieragent/plugins/tools/collect_reports.py:181 还需要按 wall-clock 剩余预算截断等待。
评测资产仍要看任务域
benchmarks 存在不代表你的私有工作流已验证。应把 sources/frontieragent/apodex/tests/test_profiles.py:112 这种 provider/runtime 测试扩展到自己的模型和沙箱。
