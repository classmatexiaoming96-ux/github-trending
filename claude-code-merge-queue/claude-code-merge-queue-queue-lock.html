FIFO queue-lock 深度解析

PID-liveness FIFO lock 如何让 build 和 land 在本机跨 worktree 串行执行。

§ 00 · DETAIL

导入链与契约

锁的公共接口

QueueLock 的公共契约很小：src/lib/queue-lock.ts:43 定义 AcquireOptions，src/lib/queue-lock.ts:48 暴露 acquire/release/lane/held。这个接口克制，意味着 build-lock 和 land 可以共用一套互斥原语，而不用各自发明不同的排队语义。src/lib/queue-lock.ts:55 的 repoKey 又把锁绑定到 git common dir，不会让同一个 repo 的多个 worktree 锁分裂。

真正的设计点在 src/lib/queue-lock.ts:73 到 src/lib/queue-lock.ts:80：queueName 决定是 build 队列还是 land 队列，repo hash 决定作用域，tickets 子目录和 lock 文件分别承担排队和持锁状态。src/lib/queue-lock.ts:82 还把当前目录名作为 lane，方便等待日志显示是哪条 lane。

§ 01 · DETAIL

核心实现逐段拆

公平队列

排队公平性来自 src/lib/queue-lock.ts:103 的 pruneDeadTickets 和 src/lib/queue-lock.ts:122 的排序。它按 timestamp 再按 pid 排序，所以不是“谁 poll 得快谁赢”。这比简单 while-lock-file-exists 更重要，因为多个 coding agent 往往会同时结束测试，公平队列能减少重复 rebase 和饥饿。

原子抢锁在 src/lib/queue-lock.ts:140。写临时文件后用 src/lib/queue-lock.ts:144 的 linkSync 建立 lock 文件：如果目标已存在，文件系统保证失败。失败后 src/lib/queue-lock.ts:154 读取 holder，并在 src/lib/queue-lock.ts:155 判断 PID 是否还活着；死 holder 会在 src/lib/queue-lock.ts:157 被回收。

关键流程

获取与释放

acquire 的循环在 src/lib/queue-lock.ts:192 开始：先写 ticket，再每轮 prune，检查自己在队列中的位置。只有 src/lib/queue-lock.ts:201 满足 ahead <= 0 且 lockFree 时才尝试拿锁。成功后 src/lib/queue-lock.ts:205 删除自己的 ticket，说明 holder 与 waiter 身份分离，队列目录不会把已持锁者重复算作等待者。

release 也保持幂等：src/lib/queue-lock.ts:167 只在 held 时删除 lock，并验证 src/lib/queue-lock.ts:170 holder pid 是自己；随后 src/lib/queue-lock.ts:179 不管是否 held 都尝试删 ticket。这让正常退出和异常恢复走同一条清理路径。

关联模块

这个锁不是孤立模块。land 在 src/land.ts:78 创建名为 land 的队列，build-lock 在 src/build-lock.ts:1 使用同类语义，而 ephemeral resource 在 src/lib/ephemeral.ts:105 把 claim/use/release 模式迁移到测试资源。换句话说，项目把“进程活性判断”作为基础工程原语复用。

src/lib/ephemeral.ts:97 · L97-126TypeScript
97/**
98 * Run `fn` against a freshly created resource, prune any orphans left by a
99 * previous crashed run first, and always release the claim — including on
100 * a thrown error. If THIS process is killed before the `finally` runs, the
101 * resource isn't leaked forever: the next call to `withEphemeralResource`
102 * (in the next test run, from any lane) prunes it via `orphans()` before
103 * creating its own.
104 */
105export async function withEphemeralResource<T>(
106  provider: EphemeralResourceProvider<T>,
107  registry: ClaimRegistry,
108  fn: (resource: T) => Promise<void>,
109): Promise<void> {
110  for (const orphan of registry.orphans()) {
111    await provider.destroyOrphan(orphan);
112    registry.release(orphan.id);
113  }
114
115  const id = `${Date.now()}-${process.pid}`;
116  const claim: Claim = { id, pid: process.pid, createdAt: Date.now() };
117  registry.record(claim);
118
119  const resource = await provider.create();
120  try {
121    await fn(resource);
122  } finally {
123    await provider.destroy(resource);
124    registry.release(id);
125  }
126}

源码判断

这套锁的优势是简单、可审计、无需 daemon；代价是只能协调一台机器。src/lib/queue-lock.ts:74 把状态放在 os tmpdir，跨机器不会共享；但这正好匹配项目定位：本地 parallel Claude Code agents 的交通灯，而不是云端 merge queue。
