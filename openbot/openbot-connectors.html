§ 02 · KEY FLOW

关键流程

▸同步游标只代表已持久化位置

cursor() → adapter.discover(cursor, mode) → persistBatch(changes,nextCursor) OR apply(change)* then commitCursor(nextCursor) → recordRun(succeeded) ↘ catch → recordRun(failed) → throw

这个流程的要点是 cursor 代表“已经安全持久化到哪里”，所以 worker/tests/connector-runner.test.ts:27 的失败测试很重要：如果 apply 抛错，worker/tests/connector-runner.test.ts:48 断言 cursors 仍为空。

§ 03 · EDGE CASES

边界 / 失败模式

▸失败不推进游标

  • worker/src/connector-runner.ts:31 在缺少 batch 和 individual write 能力时直接抛错，避免静默丢数据。
  • worker/src/connector-runner.ts:41 到 worker/src/connector-runner.ts:43 失败会记录 run failed 并继续抛出，调度层能重试。
  • worker/tests/connector-runner.test.ts:51 验证 reconcile mode 被传给 adapter，说明同步模式不是 runner 私自决定。

▸测试证据

测试证据是 成功提交 cursor 的测试从 worker/tests/connector-runner.test.ts:5 开始，runConnector 调用在 worker/tests/connector-runner.test.ts:9，cursor 初始值是 worker/tests/connector-runner.test.ts:17，结果断言在 worker/tests/connector-runner.test.ts:23；失败测试从 worker/tests/connector-runner.test.ts:27 开始，expect wrapper 在 worker/tests/connector-runner.test.ts:30，故障注入是 worker/tests/connector-runner.test.ts:40，cursor 为空由 worker/tests/connector-runner.test.ts:48 验证。这类 runner 看似简单，但它决定外部知识源是否会因为半批失败造成永久漏同步；OpenBot 把这个边界写得足够小，也足够容易测试。

从产品语义看，worker/src/connector-runner.ts:17 是后台知识同步的最小事务边界，而 app/src/lib/channels/start.ts:20 是前台会话启动的最小用户体验边界；二者都先完成必要状态写入，再暴露下一步，让用户和调度器都不会看到半完成状态。

server/src/connectors
Connector admin service 管理 tenant package 中声明的 knowledge sources。
app/src/lib/channels
UI channel flow 把 agent conversation 与缓存、导航和 optimistic first message 串起来。

这也是 OpenBot 与普通导入脚本的差异：worker/tests/connector-runner.test.ts:51 专门验证 reconcile mode 会被传给 adapter，说明同步层尊重调度者指定的运行语义；而 worker/src/connector-runner.ts:41 到失败分支只负责记录 failed 并继续抛出，让上层重试策略能够看到真实错误。

如果把 connector 看成外部知识源的事务日志，worker/src/connector-runner.ts:27 的 batch 分支适合数据库一次性 upsert，worker/src/connector-runner.ts:35 的逐条分支适合简单 adapter；两条路最终都必须等到变更落盘后才进入 worker/src/connector-runner.ts:36 的 cursor 提交，因此失败重跑最多重复处理，不会永久跳过未写入的数据。

前端 channel flow 也用同一套“先落状态再切视图”的思路：app/src/lib/channels/start.ts:21 先创建 channel，app/src/lib/channels/start.ts:22 立即把返回对象写入 query cache，app/src/lib/channels/start.ts:23 暂存用户第一条消息，然后 app/src/lib/channels/start.ts:24 才开始导航。这样首屏不会出现空 thread，也不会把用户刚输入的目标丢给后台 join 时序。
