§ 00 · OVERVIEW

它解决什么，凭什么值得拆

OpenBot 的核心问题是：如果一个 AI coworker 拥有浏览器、文件、shell 和外部工具，它怎样既能做事，又不把权限边界交给模型文本？组合根在 server/src/index.ts:297 到 server/src/index.ts:367 把 runtime、computer gateway、policy store、plugin store、channel store 和审计 store 统一装配，这说明项目把“会聊天”和“会行动”视为同一个受治理系统，而不是两个孤立功能。

源码最强的地方是边界分层：身份用 server/src/index.ts:58 和 server/src/index.ts:100 统一解析，电脑动作必须穿过 server/src/computer/gateway.ts:309，真实浏览器动作在 agent-computer/src/index.ts:27 后的独立进程里执行，Docker socket 则被缩到 supervisor/src/index.ts:14 描述的 supervisor 词汇。这样的拆分让每个风险面都有明确所有者。

▸亮点

源码亮点 1
Policy gateway 把 ref 解析、策略判断、审计写入和真实动作串成唯一通道，拒绝动作不会到达 computer。
源码亮点 2
Computer supervisor 把 Docker socket 缩成 Bot 语义词汇，API server 即使被打穿也不能任意操作 Docker。
源码亮点 3
Human handoff 是独立 state machine，拒绝两个驾驶者同时控制同一页面，secret value 不进状态。
源码亮点 4
Connector runner 支持 batch 或逐条持久化，并且失败时不推进 cursor，适合知识源同步。

▸风险

部署复杂度
OpenBot 横跨 server、worker、supervisor、agent-computer、app 和数据库，首次部署比单进程 agent harness 重。
策略表达能力
CEL 带来灵活性，也要求运营方理解规则失败会 fail-closed；误写规则可能阻塞真实工作。
共享电脑模式
provider.ts 明确指出 shared provider 会共享浏览器会话、文件和登录，生产应使用 per-bot supervisor。
源码体量快速增长
项目刚创建几天已有大量测试和子包，架构在快速变动，二次开发需要紧跟接口变化。
