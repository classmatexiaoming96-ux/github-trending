§ 00 · OVERVIEW

它解决什么，凭什么值得拆

deer-workflow 的入口不是把 prompt 丢给某个模型，而是先把 Workflow 当成可加载模块处理：src/flow/workflow.ts:90 定义泛型 workflow()，src/flow/workflow.ts:94 读取父上下文，src/flow/workflow.ts:101 解析脚本路径，src/flow/workflow.ts:102 组装执行上下文，src/flow/context.ts:30 再用 AsyncLocalStorage 绑定异步调用链。因此它解决的是 Agent 任务编排的可观察运行时，而不是又一个聊天封装。

它值得拆的原因在于边界很清楚：src/flow/types.ts:60 把 workflowId、parentId、depth、scriptPath 和 args 固定成执行契约，src/flow/types.ts:119 把 meta 约束成 name、description、phases 与 exampleArgs，src/flow/workflow.ts:232 强制 kebab-case，src/flow/workflow.ts:246 要求 phases 非空，src/flow/workflow.ts:271 还会解析 JSON-safe exampleArgs。这里的设计目标是让自动化可以读懂一条工作流，而不是只能读自然语言说明。

▸为什么不是普通脚本

执行路径的关键是事件先行：src/flow/workflow.ts:110 进入 workflow context 后，src/flow/workflow.ts:112 先发 workflow:start，src/flow/workflow.ts:123 在发现 metadata 后发 workflow:meta，src/flow/workflow.ts:131 成功时发 workflow:end，失败时由 src/flow/workflow.ts:139 发 workflow:error。这个顺序让 TUI、JSONL writer 和外部监控都能以同一事件协议观察任务。

§ 05 · HIGHLIGHTS

技术亮点

上下文显式
从打包面看，package.json:6 暴露 deer-workflow CLI，package.json:9 到 package.json:16 暴露 agents、events、flow、logging、runner 等子路径，src/index.ts:1 到 src/index.ts:5 再做统一 export。这个 API 面积不大，但它把 Agent 运行时、流程原语和事件协议放在同一个包里，适合作为 coding-agent workflow 的轻量底座。
事件可机器消费
Runner 和 EventEmitter 让命令行、TUI、日志和自动化共享同一事件协议。
§ 06 · RISKS & GAPS

技术亮点之外，别忽略这些

▸上线前需要补的工程约束

需要注意的短板同样来自源码：src/flow/workflow.ts:20 把嵌套深度限制为 1，复杂 DAG 需要在用户层拆解；src/flow/pipeline.ts:91 和 src/flow/parallel.ts:29 都把错误吞成 null，调用者必须主动检查；src/agents/claude-agent.ts:191 与 src/agents/codex-agent.ts:205 依赖 Bun.which 查 CLI，可移植性取决于宿主环境。

嵌套深度
MAX_NESTED_WORKFLOW_DEPTH 只允许一层嵌套，复杂 DAG 需要自行拆分。
错误语义
parallel/pipeline 用 null 表示失败，调用者需要建立显式结果校验。
