一句话定位：给 coding agent 装一个“预先建好的代码地图”。当 agent 需要理解代码时，不再 grep 满仓库，而是向 CodeGraph 的 MCP 服务发一次结构化查询，一个调用拿到入口点、相关符号、调用关系和源码片段。作者强调一个关键设计哲学——抽取过程是确定性的，源自 AST 而非 LLM 总结，因此结果稳定、可复现、可进 git。

数据模型：22 种节点 × 12 种边

图的表达力来自精心设计的类型系统（src/types.ts）。节点（NodeKind）覆盖 22 种符号——从 function/method/class 到 interface/trait/route/component；边（EdgeKind）覆盖 12 种关系：

// 12 种关系，每条边还带 provenance：'tree-sitter' | 'scip' | 'heuristic'
export type EdgeKind =
  'contains' | 'calls' | 'imports' | 'exports'
  | 'extends' | 'implements' | 'references' | 'type_of'
  | 'returns' | 'instantiates' | 'overrides' | 'decorates';

interface Edge {
  source: string; target: string; kind: EdgeKind;
  line?: number; provenance: Provenance;  // 谁推断出这条边
}

抽取层：19+ 语言的 WASM 解析

CodeGraph 用 web-tree-sitter + tree-sitter-wasms 跑 WASM 语法，不依赖任何原生编译，因此“一个二进制到处跑”。它对工程细节的打磨令人印象深刻：

  • 按需加载语法：只为项目里真实出现的语言编译 WASM grammar，控制内存。
  • Worker 每 250 文件回收一次（WORKER_RECYCLE_INTERVAL）：因为 WASM 线性内存只增不减，唯一回收堆的办法就是杀掉 isolate 重建。
  • 1MB 文件上限 + 10s 解析超时：跳过压缩 bundle / vendored 大文件，避免撑爆 WASM 堆。
  • Git 感知发现文件：git ls-files --recurse-submodules，尊重 .gitignore 与子模块。
  • 对 Svelte / Vue / Liquid / Delphi 表单（.dfm）这类 tree-sitter 搞不定的格式，写了专用 extractor。

解析层：tree-sitter 搞不定的，才是真功夫

这是 CodeGraph 最有价值的部分。tree-sitter 只能告诉你“这里有个调用”，却无法跨文件解析“它到底调的是谁”，更无法理解框架的动态分发。ReferenceResolver 用一套分层策略来补这个洞：

  • ① 内置过滤：跳过 stdlib / 内建函数（JS 内建、React hooks、Python 内建、Go stdlib…）。
  • ② 框架模式：识别 14+ 框架（Express / NestJS / Django / Laravel / Rails / Spring / Gin / Axum / ASP.NET / Vapor / SvelteKit / Vue-Nuxt / Drupal…），把 URL 路由 route 节点 连到处理函数。这里用的是对“去注释后源码”的正则，而非完整 AST，省开销。
  • ③ import 解析：按语言扩展名顺序解析（TS 会试 .ts/.tsx/.d.ts/index.ts…），并读 tsconfig 的 paths 别名、Cargo workspace 成员。
  • ④ 名称匹配：精确名 → 限定名 → 文件路径三级匹配，用路径邻近度给候选打置信分。
  • ⑤ 回调合成（最妙）：见下。
回调合成 callback-synthesizer：tree-sitter 永远追不到 emitter.on('mount', handler) 和 emitter.emit('mount') 之间的隐式调用。CodeGraph 主动“合成”这些边——它识别注册器（/^on[A-Z]|subscribe|addListener/）与派发器（/emit|trigger|notify|dispatch/），按字段名/事件字符串配对，凭空补出 React 重渲染、EventEmitter、Vue/Svelte 组合式的动态调用边，并打上 provenance:'heuristic' 标注合成来源与注册位置。

存储层：node:sqlite + FTS5

CodeGraph 直接用 Node 内置的 node:sqlite（DatabaseSync，真正的 SQLite 编进了 Node），外面包了一层 better-sqlite3 形状的接口。因为自带 Node runtime，所以 WAL、FTS5 全平台可用。它的 PRAGMA 调优很“数据库工程师”：

src/db/index.ts — 连接调优
db.pragma('journal_mode = WAL');      // 读不阻塞写，MCP+git hook+CLI 可并发
db.pragma('synchronous = NORMAL');    // 配合 WAL 安全
db.pragma('cache_size = -64000');     // 64MB page cache
db.pragma('mmap_size = 268435456');   // 256MB 内存映射 I/O
db.pragma('busy_timeout = 5000');      // 锁等待 5s，骑过正常 sync

schema 设计同样克制：edges 表只建 (source,kind) 与 (target,kind) 两个复合索引，靠左前缀扫描覆盖正反向查询，故意不建多余的单列索引以减轻写入负担；unresolved_refs 表把引用解析延后到抽取之后，避免抽取阶段 N+1 查符号表；nodes_fts 用 FTS5 虚拟表 + 触发器自动同步全文索引。

一个被低估的细节：explore 工具的自适应预算会随项目规模缩放——小项目单次给 18K 字符、大项目（≥25k 文件）给到 38K，每行还带 cat -n 式行号前缀，让 agent 能直接引用 file:line 而无需回读文件。还有一条硬不变量：单文件字符上限在任何档位都不能下降——这是被一个真实回归逼出来的（excalidraw 的 415KB App.tsx 曾因上限太低只返回不到 1% 内容，迫使 agent 退回去 Read）。

对 coding agent 生态的意义

CodeGraph 把“代码理解”从 每次会话临时探索 变成 一次索引、长期复用的基础设施。它选择 100% 本地 + 确定性抽取，意味着结果可复现、可进 git、无隐私顾虑——这让它有资格成为多种 agent 共享的“代码索引标准件”。它证明了一件事：agent 性能的下一个数量级，可能不在更大的模型，而在更好的检索基建。

语义批处理：用社区发现切批次

朴素的“每 20 个文件一批”会把逻辑耦合的模块拆散，丢失跨批的语义边。Understand-Anything 在 2026-05 的设计里引入了一个聪明做法（compute-batches.mjs）：对 import 图跑 Louvain 社区发现，把语义耦合的文件聚成一批（5–35 个/批），超大社区再用边介数启发式拆分；同时为每个文件构造 neighborMap（跨批邻居导出的符号），让 file-analyzer 能自信地下跨批边的判断。这同时解决了另一个现实问题——在输出受限的后端（如 Bedrock Opus 4096–8192 token）上，agent 会自检输出大小并切成 batch-i-part-k.json。

指纹 + 陈旧检测 = 增量分析

fingerprint.ts 为每个文件算出结构指纹（内容 hash + 函数/类/import 签名）。变更被分成三级：NONE（hash 相同，跳过）/ COSMETIC（内容变但签名没变，只更新语义）/ STRUCTURAL（签名变，全量重分析）。配合 git diff 找出改动文件，只重分析它们，再 merge 回旧图——200 文件的库改了 3 个文件，秒级更新而非分钟级。

搜索：模糊 + 语义双引擎

搜索走 fuse.js 做关键词模糊匹配（name/tags/summary 加权），同时有一个 SemanticSearchEngine 对预计算 embedding 做余弦相似度检索，Dashboard 里可在 fuzzy / semantic 间切换。一个值得称道的隐私细节：写盘前 sanitiseFilePaths 会把所有绝对路径转成项目相对路径，绝不把 /Users/alice/company/... 泄漏进可提交的 JSON。

前端用 React Flow 渲染图、Zustand 管 150+ 字段的状态、ELK（Eclipse Layout Kernel）做层次布局、Louvain 做视觉聚类、Prism 高亮源码。三种视图（structural / domain / knowledge）可切换；还有角色自适应 UI——根据你是“非技术 / 初级 / 资深”动态调整细节密度，以及暗金奢华主题（#0a0a0a + 金色 #d4a574 + DM Serif Display）与 6 国语言本地化。

真正的护城河：七条治理流水线

普通插件市场（npm 之类）几乎没有审查。Anthropic 把“官方”做成了一套可审计、可自愈的 CI/CD 治理体系，跑在 .github/workflows/ 里：

  • validate-plugins：PR 时校验结构与 schema，对官方市场而言 SHA 锁定缺失 = 硬错误。
  • scan-plugins（核心）：用 Claude 本身按 policy/prompt.md + schema.json 对每个外部插件做安全策略扫描，输出结构化裁决：是否联网、是否下载软件、hook 是否“宽作用域”、是否有未披露的遥测、描述是否与行为相符。裁决带 30 天缓存（按策略 hash），策略一改全部失效。用 WIF 联合身份鉴权，无静态 API key。
  • bump-plugin-shas：每晚 07:23 UTC 自动追踪上游 HEAD，新 SHA 先 validate 再开一个汇总 PR，并触发扫描；单次最多 130 个，防成本失控。
  • revert-failed-bumps：若扫描发现某插件策略不过，自动把它的 SHA 回滚到主干值、重扫、在 PR 上评论违规项——一个坏上游不会卡住整批 bump。带 3 次/晚的熔断防循环。
  • check-mcp-urls：每日探活所有 http/sse MCP 端点，404/410/连接失败即报警。
  • validate-frontmatter：用 Bun + yaml 校验 agents/skills/commands 的 YAML frontmatter（含 glob 特殊字符处理）。
  • close-external-prs：官方市场只收 Anthropic 成员的 PR，外部贡献自动关闭并引导到提交表单。
用 LLM 审 LLM 的生态：最值得玩味的一点——scan-plugins 让 Claude 去读每个第三方插件的 hook handler、MCP server、skill 源码，判断它是否会偷偷联网、是否名实不符。这是“AI 安全审查 AI 工具”的一次工程化落地，也是“官方市场”相比裸 GitHub 仓库最硬的差异化。

Canonicalize：把异构源压成同一种 Markdown

src/openhuman/memory/tree/canonicalize/ 下每种源一个适配器，全部产出同一个 CanonicalisedSource { markdown, metadata }。各适配器的处理细节很克制——拒绝在这一层做"理解"：

  • chat.rs：消息按时间戳防御性排序，每条以 ## YYYY-MM-DDTHH:MM:SSZ — User 起头；空 batch 直接返回 Ok(None) 让上层跳过。
  • email.rs：每封邮件之间用 ---\nFrom: 分隔；正文先过 email_clean::clean_body() 把引用历史、退订链接、营销页脚剥掉——给后面的摘要器一个信号干净的输入。
  • document.rs：本身已经是 Markdown 或纯文本，加一点 front-matter 就送下游。

Chunker：内容寻址的确定性 ID

这是整个系统能"幂等"的根因。chunk 的 ID 不是自增的，而是对内容求 SHA-256 取前 32 位十六进制。同一段输入永远算出同一个 ID，重复 ingest 直接 upsert，从源头杜绝重复。

src/openhuman/memory/tree/types.rs — 确定性 chunk_id
pub fn chunk_id(
    source_kind: SourceKind,
    source_id: &str,
    seq_in_source: u32,
    content: &str,
) -> String {
    let mut hasher = Sha256::new();
    hasher.update(source_kind.as_str().as_bytes());
    hasher.update([0u8]);
    hasher.update(source_id.as_bytes());
    hasher.update([0u8]);
    hasher.update(seq_in_source.to_be_bytes());
    hasher.update([0u8]);
    hasher.update(content.as_bytes());
    // → SHA256 取前 32 位 hex（128-bit，单用户 workspace 抗碰撞绰绰有余）
}

注意 content 也参与了哈希——这就允许同一来源在不同时间窗内有相同 seq_in_source 而仍然产生唯一 ID（比如 Slack 每 6 小时一桶，每桶 seq=0 起，但内容不同所以 ID 不同）。这是个不张扬但关键的设计取舍。

  • mem_tree_chunks —— 主表，128-bit ID + 来源/时间/owner 索引。
  • mem_tree_chunk_embeddings —— 按 model_signature 存向量 BLOB，支持多模型并存方便迁移。
  • mem_tree_score —— 每条 chunk 的全部信号分项（token / unique words / metadata / source / interaction / entity_density），可审计。
  • mem_tree_entity_index —— 实体倒排表，(entity_id, node_id) 主键，节点跨 chunk 与 summary。
  • mem_tree_trees / mem_tree_summaries / mem_tree_buffers —— 三棵树的状态机。
  • mem_tree_hotness —— 实体热度分（驱动 topic tree 物化）。
  • mem_tree_jobs —— 持久化作业队列（下一节展开）。

Scoring：两段式打分 + 准入门

分数控制"这条 chunk 配不配进树"。设计上分两段：快速路径在 ingest 同步阶段就跑，只用 token 数、词汇多样性这种纯启发式；慢速路径在 worker 上跑，做 LLM 实体抽取与 embedding。两个阈值把分数切成三段：

src/openhuman/memory/tree/score/mod.rs — 准入决策
pub struct ScoringConfig {
    // ...
    pub drop_threshold: f32,                // 默认 0.30
    pub definite_keep_threshold: f32,     // 默认 0.85 — 这分以上免 LLM 直接收
    pub definite_drop_threshold: f32,     // 默认 0.15 — 这分以下免 LLM 直接丢
}

// 决策伪码：
// fast >= 0.85   → admit                    (no LLM)
// fast <= 0.15   → drop                     (no LLM)
// 0.15 .. 0.85   → 调 LLM 实体抽取做二次判定 (borderline 才烧 token)

这个设计意图明确：用启发式吃掉两端的"显然要 / 显然不要"，把宝贵的 LLM 调用集中在中间灰区。准入失败的 chunk 不会被删——mem_tree_score.dropped = 1 记着，原文还在 vault 里，只是不会再被树或检索引用。这保留了完整溯源能力。

第二层 · 系统之心

三棵树，三种问题

Memory Tree 的招牌不是"一棵更复杂的树"，而是三棵独立、互不干扰的树同时生长，每棵回答一类不同的检索需求。它们都吃同一个 leaf 流，但封口规则、标签策略、时间窗各不相同。

SOURCE
源树 · per-source 滚动缓冲

每个 Slack 频道 / Gmail label / 文档一棵。新 leaf 进 L0 buffer，攒够就封成 L1 摘要，继续往上级联。

  • L0 封口：50k token 或 10 个 sibling
  • L1+ 封口：10 个 sibling（按数不按 token）
  • 过期强封：7 天没动也封
TOPIC
主题树 · 按"热度"懒物化

每个高热度实体（人、项目、ticker、repo）一棵。冷实体连树都不建；热度越高，刷新越积极。

  • 热度 = ln(30d 提及数) + 跨源数 + 近期衰减 + 中心度 + 用户查询权重
  • 由 topic_route 作业按门槛触发建树
  • 结构和源树相同，schema 共用
GLOBAL
全局树 · 每日一节点

单例。每天 UTC 零点后调度器跑一次，把昨天跨所有来源的最佳 L1+ 摘要合成成一节日报。

  • L0 = 日报；攒够 10 个升级 L1（周）
  • L1 升 L2（月）、L3（年）逐级展开
  • 跑出来的标签是 UnionFromChildren，免再调一次 LLM

桶封 (bucket-sealing) 的关键常量

tree_source/types.rs 直接把这套规则写成常量：

src/openhuman/memory/tree/tree_source/types.rs:188
pub const INPUT_TOKEN_BUDGET: u32 = 50_000;
pub const OUTPUT_TOKEN_BUDGET: u32 = 5_000;
pub const SUMMARY_FANOUT: u32 = 10;
pub const DEFAULT_FLUSH_AGE_SECS: i64 = 7 * 24 * 60 * 60;

// should_seal: L0 看 token 预算，L1+ 看兄弟数
pub fn should_seal(buf: &Buffer) -> bool {
    if buf.level == 0 {
        buf.token_sum >= INPUT_TOKEN_BUDGET as i64
            || buf.item_ids.len() as u32 >= SUMMARY_FANOUT
    } else {
        buf.item_ids.len() as u32 >= SUMMARY_FANOUT
    }
}

为什么 L0 按 token、L1+ 按数？一个非常工程师的考虑：summarizer 的输出长度有时长有时短。如果 L1 也按 token 封，万一摘要器吐得很短，L1 buffer 就要凑很多条才达到 50k token，造成"长链条窄树"。改成按 10 个 sibling 封口能保证树形结构稳定地"宽展开"——一棵看起来像树的树，而不是退化的链表。

级联封口（cascade seal）：当 L0 封成 L1，会立刻检查 L1 buffer 是否也到达门槛；到了就再封一层。一次 50k token 的注入可能一路级联到 L3。这套递归在 bucket_seal.rs::cascade_seals() 里完成，全程在一个 SQLite 事务内。

主题树的热度公式：用对数压住头部、奖励跨源

这是 tree_topic/hotness.rs:32 里非常值得品的设计——它在五个因子上做加权和，每个都有明确的物理意义：

src/openhuman/memory/tree/tree_topic/hotness.rs
pub fn hotness(entity_id: &str, idx: &EntityIndexStats) -> f32 {
    let mention = ((idx.mention_count_30d as f32) + 1.0).ln();     // log 压头部
    let source  = (idx.distinct_sources as f32) * 0.5;           // 跨源加分
    let recency = recency_decay(idx.last_seen_ms, now_ms);     // 分段线性衰减
    let central = idx.graph_centrality.unwrap_or(0.0);           // 图中心度 (Phase 4+)
    let query   = (idx.query_hits_30d as f32) * 2.0;             // 用户问了几次
    mention + source + recency + central + query
}

recency_decay 是分段线性的：≤1 天 = 1.0，1–7 天线性降到 0.5，7–30 天降到 0，再老不计入。这避免了指数衰减把"两个月前但很重要"的实体直接清零，又让 30 天的天花板硬性截断。query 权重 ×2 表达了一个朴素但正确的偏好：你查过的，比别人提过的更值得维护一棵树。

标签策略：三种打标方式

摘要节点封口时还要决定"这一节摘要的标签从哪来"。LabelStrategy 给了三个选项：

  • ExtractFromContent：对刚生成的摘要文本再跑一次实体抽取——能捕捉到"几条 leaf 各说一点、合起来才浮现的主题"。源树、主题树用这个。
  • UnionFromChildren：把子节点已有的实体/topic 去重并取并集——免一次 LLM 调用。全局树用这个，因为它的子节点本身就是已经被 L1 抽取过的源摘要。
  • Empty：留空，留给后续阶段填，防止跨树污染。
第三层 · 作业系统

慢活全部丢给队列，UI 永不阻塞

ingest 在热路径上只做"切碎、快速打分、入库、入队"。所有真正烧资源的事情——embedding、实体抽取、摘要生成、级联封口、日报合成——都被推进一个持久化的 SQLite 作业队列，由后台 worker 池跑。

六种作业类型

Kind做什么同步 / 异步调 LLM
extract_chunk深度打分 + 实体抽取；决定 admitted / dropped异步是
append_buffer把 admitted leaf 推进树的 L0 buffer；可能触发 seal异步否
seal把 buffer 压成一节摘要；视情况向上级联异步是（summarizer）
topic_route把 leaf 按实体路由进主题树（热度门控）异步是

flush_stale巡视 L0 buffer，强制封口超过 7 天没动的异步否

Workers：三个协程 + 一个 LLM 信号量

默认 3 个 worker 协程，循环从 mem_tree_jobs 表里抢 status='ready' 且 available_at_ms <= now 的作业。一个细节非常用心：所有标记 is_llm_bound()=true 的作业，在执行前必须从一个全局信号量获取许可——这把 LLM 并发调用上限锁住，防止"一次性接入 10 个 Slack 频道"把 embedding API 打到 rate-limited。

领到作业后，worker 立刻把行标记成 running，写入自己的 worker_id 与 lease_until_ms。如果它崩在中间，下一轮启动时 recover_stale_locks() 会扫到 lease 已过期的行，把它们重置回 ready 让别的 worker 重做。

失败处理：指数退避 + 显式 Defer

作业返回三种结果：Done 完成；Defer { until_ms, reason } 不消耗重试预算地延后（用于 LLM 限流这种瞬时不可用）；Err 真失败——按 2^attempts 秒指数退避丢回队列；超过 max_attempts（默认 5）就标 failed 进死信。

Scheduler：唯一的"墙钟"心跳

日历驱动的工作（日报、周强封）由一个独立的 scheduler 协程发起。它每天 UTC 大约 00:05 醒一次，向队列推两件事：

  • DigestDaily(yesterday) —— 合成昨天的全局日报
  • FlushStale(today) —— 检查所有 L0 buffer 中年龄 ≥7 天的，强制封口

scheduler 自己绝不执行 summarizer——它只发作业，让重试、去重、stale-lock 恢复都从作业队列统一走。这是个非常老练的"职责分离"设计。

Dedupe key 防重发：mem_tree_jobs.dedupe_key 是 UNIQUE 列，"digest_daily:2026-04-21" 这种键的第二次插入会直接被 SQLite 约束挡掉。即使 scheduler 重启两次，也只会有一份日报作业排队。

有 query 时走 hybrid：embedding 算余弦相似 → 与 BM25-ish 结构分加权 → 加入 recency → 如果 query 里包含已知实体名，命中实体的节点再加权。无 query 时则纯按时间和结构分排序，这让"列出最近的"和"语义搜索"是同一个入口的两种用法。

溯源：每个 hit 都带 provenance

命中里有 source_ref（永久指向 Slack 消息 / Gmail 线程 / 文档段落的不透明指针），UI 上点 hit 就跳回 Obsidian vault 的原文件。这一点彻底解决了"AI 模糊地引用一句话但说不出哪来"的问题——所有摘要都能被打开还原成它的全部子节点和原始 chunk。

Agent 怎么用：DefaultMemoryLoader 注入

agent 端的 memory_loader.rs 在每次用户发消息时调 memory.recall(user_msg) 取相关条目，然后把它们组织成四个段落注入 system prompt：

  • [Memory context] —— 语义召回的相关记忆
  • [User working memory] —— ≤3 条用户画像（时区、偏好）
  • [Cross-chat context] —— 其他对话线程里的近期命中
  • [Prior conversations] —— 之前会话里的高优先 episodic 条目

SessionMemoryState：用三个增量决定何时抽取

context/session_memory.rs 跟踪当前会话的累计 token、tool 调用数、turn 数。只有这三个增量同时跨过门槛（token +4000、tool +8、turn +4）才会触发后台的"档案管理员"子代理把会话压成结构化记忆条目——避免每隔几句话就启一次抽取作业。

护栏

本地存储，但不等于裸奔

所有数据都不出机器，但"不出机器"不代表"可以随便存"。memory/safety/mod.rs 在写入与索引时就做了四类拦截，故意倾向于宁可误删也别留下密钥的"保守派"策略。

  • Block 模式（直接删）：PEM 私钥（RSA / EC / OpenSSH / PGP 各变体），高熵 base64 段。
  • Redact 模式（替换为 [REDACTED]）：Bearer token、AWS AKIA…、GitHub gh*_、Anthropic sk-ant-…、Google AIza…、OpenAI / Stripe sk|rk_live|test_…、Slack xox[abprs]-…、JWT、OAuth。
  • Key Redaction：JSON 里 "api_key" / "token" / "password" / "secret" 这种键的值，直接擦掉——不管值长啥样。
  • Depth Limit：深嵌套 JSON 做截断防 DoS。

这套清洗发生在三个时机：写入 chunk 前、抽取实体前、把记忆切片写进日志前。"宁可误擦"的取向意味着偶尔会把无害字符串当成 token 扔掉，但绝不会让一个真 token 进入摘要再被某天的检索意外暴露给 LLM。

合而观之

为什么不是又一个向量库

把所有细节合起来看，Memory Tree 与"套壳向量库"差的不是某一个特性，而是把记忆当作什么的根本分歧。

可选后端：兼容 agentmemory

值得一提的是 OpenHuman 没有把自己锁死。MemoryConfig.backend = "agentmemory" 可以让它把存储层换成另一个独立项目 agentmemory 的 REST 服务——这样多个 coding agent（Claude Code、Cursor、Codex、OpenCode、OpenHuman）可以共享同一个持久化记忆。Memory Tree 流水线本身仍在跑，但底层 Memory trait 的存储被换掉。这种"流水线 + 后端"解耦的态度，比大多数声称要做生态的项目都更脚踏实地。

对个人 AI 的意义

Memory Tree 的真正价值在两件事上。第一，它示范了"确定性流水线 + LLM 重活异步化"这种组合拳——把可以确定的部分（切分、哈希、入库、调度）做得像数据库一样稳，把 LLM 调用约束在借灰区判断、摘要生成这种能容忍重试和失败的位置。第二，它把"个人 AI 的记忆"从云服务的私有 schema 抢回了用户的硬盘——你可以打开 ~/.openhuman/wiki/ 直接用 Obsidian 读，可以 git 化、可以备份、可以审计、可以删。本地优先不是宣传话术，而是体现在每一个文件路径里。

① 多 Agent Session 架构：一个 Session，N 个隔离 Agent

kimi-code 的「多 Agent」不是把一个大上下文切片，而是真正实例化多个独立 Agent 对象。Session 是容器，持有一张 agents: Map<string, Agent>；主 agent（type:'main'）启动时创建，subagent（type:'sub'）则在运行期由 SessionSubagentHost 按需 spawn。每个 Agent 都自带独立的 Kaos 执行环境、ToolManager、PermissionManager、AgentRecords（独立 wire.jsonl）、以及独立的 context.history——所以子 agent 探索时塞满的上下文，不会污染主 agent 的窗口。这正是「explore 子代理读 50 个文件，主 agent 只收到一段 200 字摘要」的实现基础。

关键在于父子之间只通过「一次 prompt 进、一段 summary 出」通信。spawn() 先解析 profile（coder / explore / plan），用父 agent 的 rawGenerate 创建子 agent，再用 linkAbortSignal 把父信号挂到子 AbortController——父一旦中断，子立即级联 abort。子 agent 跑完后只回传 lastAssistantText，且有一条「摘要太短就重跑」的兜底：少于 200 字符触发一次 SUMMARY_CONTINUATION_PROMPT 续写。

session/subagent-host.ts — spawn() 隔离创建
async spawn(profileName, options): Promise<SubagentHandle> {
  options.signal.throwIfAborted();
  const parent = this.session.agents.get(this.ownerAgentId);
  const profile = this.resolveProfile(parent, profileName);  // coder|explore|plan

  // ① 创建一个全新的 Agent 实例（独立 Kaos / Tools / Records / context）
  const { id, agent } = await this.session.createAgent(
    { type: 'sub', generate: parent.rawGenerate }, undefined, this.ownerAgentId,
  );

  // ② 父信号 → 子 controller，父 abort 时子级联 abort
  const controller = new AbortController();
  const unlink = linkAbortSignal(options.signal, controller);

  const completion = this.runChild(parent, id, agent, profile.name,
    { ...options, signal: controller.signal },
    () => this.configureChild(parent, agent, profile), // 继承 cwd/model/thinking
  ).finally(() => { unlink(); this.activeChildren.delete(id); });
  return { agentId: id, profileName: profile.name, resumed: false, completion };
}

explore 子代理的冷启动优化：因为 explore agent 从空上下文出发，runChild 会在 prompt 前注入一段 collectGitContext() 的仓库快照（当前分支、最近 commit、改动文件），让它「落地即知身在何处」。这是个很小但很关键的细节——别的 subagent 没有这个待遇。

② Agent Turn Loop：runTurn / executeLoopStep 双层收敛

turn loop 被刻意拆成两层无状态函数，状态全部外置到 Agent，所以 loop 本身可独立单测。外层 runTurn() 管「turn 级收敛」：循环边界 abort、max-step 保护、usage 聚合，以及一个微妙的「非工具停止后是否继续」决策；内层 executeLoopStep() 管「单 step 原子操作」：pre/post hook、构建消息、原子 step envelope、LLM 调用 + retry、工具批处理。两者的分界点是 stopReason === 'tool_use'——它不是终止信号，而是循环控制信号：有工具调用就 continue 进下一 step，没有才进入「要不要收尾」判断。

一个容易被忽略但很重要的设计：usage 在 LLM 返回后立即记账，而不是等工具执行完。这样即使工具执行期间用户 abort，已经消费的 token 也不会丢——计费/预算永远准确。TurnFlow 是对外的发射器，持有 activeTurn 状态和一个 steerBuffer：当一个 turn 正在跑时，新输入走 steer() 被 buffer 起来（而非并发启动），turn 间隙再注入；如果没有活跃 turn，steer 等价于 prompt 直接 launch。launch 里那句 turn.agent_busy 错误就是并发 turn 的硬防线。

③ Kosong：把 5 类 LLM 协议压平成一个 ChatProvider

kosong 是纯粹的数据转换层，不含任何业务逻辑——这是它能被独立发布、独立测试的原因。createProvider(config) 是工厂，按 config.type 分发到六种实现，注意 vertexai 复用了 GoogleGenAIChatProvider，所以代码里其实是 5 个 adapter 服务 6 种 provider type。每个 adapter 干的是同一件事：把自家 SDK 的流式事件，翻译成 kosong 统一的 StreamedMessagePart 序列，并把自家的 finish_reason 归一到 6 值枚举。

generate() 的核心难点是并行工具调用的参数 delta 会交错：provider 流里 tool-call A 的参数片段和 tool-call B 的可能交替到达，所以维护了一张 toolCallIndexMap: Map<index, arrayIdx> 把碎片路由回正确的 toolCall。也因此，onToolCall 回调只在流完全结束、参数合并完成后才触发——delta 期间只更新 UI，不当真。最后一道闸是 isEmptyMessage：既无 text 又无 tool_calls 就抛 APIEmptyResponseError（reasoning 模型把预算全耗在 reasoning_content 上、content 为空，正是这个坑）。

④ Wire Records / Replay：每个动作都是一行 JSONL

这是 kimi-code 最有辨识度的能力。系统里没有可变的"会话状态对象"被直接持久化——取而代之，每个状态变化都被记成一条结构化 AgentRecord，append 进 wire.jsonl（每行一个 JSON）。记录类型有 20+ 种：turn.prompt / turn.steer / config.update / permission.set_mode / usage.record / context.append_message / context.append_loop_event / full_compaction.begin / full_compaction.complete / tools.register_user_tool …。重启恢复时，AgentRecords.restore() 把 _restoring 置 true，逐行回放 restoreAgentRecord，每种类型映射到对应的 agent 内部方法。

恢复期的硬契约：restore 不得产生任何副作用——不调 LLM、不执行工具、不碰文件系统。它纯粹是「把日志重演成内存状态」。ReplayBuilder 只在 restoring 模式下收集记录用于可视化（apps/vis 调试器就吃这个格式）。这套 wire-first 设计带来三个直接好处：① 崩溃后能精确恢复到包括 pending turn 的状态；② 跨客户端重放同一会话；③ 协议版本升级时用 migrateWireRecord 做逐条迁移（v1.1 / v1.2 迁移器就在 records/migration/）。

⑤ McpConnectionManager + OAuth：401 不是错误，是"该登录了"

McpConnectionManager 为每个 Session 持有全部 MCP server 的生命周期。connectAll 用 Promise.allSettled 并行连接、故障隔离——一个崩掉的 server 绝不阻塞 Session 启动。每个 entry 有五态机：pending → connected / failed / disabled / needs-auth，状态变化通过 onStatusChange 推给 TUI。stdio 走 StdioMcpClient（子进程 + stderr 快照用于报错），HTTP 走 HttpMcpClient。还有一个 attemptId 单调递增的陈旧回调防护：reconnect 期间老连接的 onUnexpectedClose 回来时，isCurrent() 发现 attemptId 不匹配就丢弃，避免老连接的事件污染新状态。

OAuth 的精髓在「何时不挂 provider」：对没有静态 bearer token 的 HTTP server，首次连接故意不挂 OAuth provider，让 401 干净地冒成 UnauthorizedError，从而把 entry 翻成 needs-auth（而不是 failed）——这样用户能看到 run /mcp-config login <name> 的可操作提示。只有当 hasTokens() 已经有盘上 token 时，才把 provider 挂上去让 SDK 在 401 时自动刷新。真正的浏览器授权由 McpOAuthService.beginAuthorization 驱动：起一个一次性 localhost 回调监听 → 推进 SDK auth() 拿到授权 URL → 用户浏览器完成 → complete() 校验 state（防 CSRF）后换 token。整条流程通过一个合成工具 mcp__<server>__authenticate 暴露给对话，授权成功后 reconnect 把合成工具替换成真正的 MCP 工具。

⑥ Context Compaction：0.85 触发、保留近 3 步、每 turn 最多 3 次

压缩策略 DefaultCompactionStrategy 的阈值全部是可读的常量：triggerRatio = 0.85（用量达到 max_context 的 85% 触发）、reservedContextSize = 50_000（再留 5 万 token 余量，used + reserved ≥ max 也触发）、maxCompactionPerTurn = 3（一个 turn 内最多压 3 次，超了抛 CONTEXT_OVERFLOW）。blockRatio 默认等于 triggerRatio——这是个有意的开关：两者相等时checkAfterStep 为 false，禁用异步压缩，压缩只在 beforeStep 同步阻塞式发生（block() await 压缩 worker 完成），保证下一步 LLM 调用一定在安全窗口内。

computeCompactCount 是算法核心：从尾部往前扫，保护最近 3 步 + 尾部连续的 user 消息 + 占比不超过 20% 的近期内容，找一个「角色边界」作为 splitAt——只在 m1.role !== m2.role 且不会切断 user→assistant 配对、且 m2 不是 tool 消息处切分，避免把一个 tool_call 和它的 tool_result 拆散。被切走的前半段连同一条 COMPACTION_INSTRUCTION 喂给 LLM 生成摘要，摘要 + 保留的近期消息构成新 history。压缩 worker 跑完还会逐条比对 history 是否被改过（比如用户中途 undo），变了就 cancel() 放弃这次压缩结果——绝不把摘要套到一个已经变化的历史上。

⑦ Lifecycle Hooks：13 种事件 × 外部命令门控

HookEngine 是一个把外部 shell 命令挂到 agent 生命周期的引擎。HOOK_EVENT_TYPES 定义了 13 种事件：PreToolUse / PostToolUse / PostToolUseFailure / UserPromptSubmit / Stop / StopFailure / SessionStart / SessionEnd / SubagentStart / SubagentStop / PreCompact / PostCompact / Notification。注册时按 event 归桶（byEvent: Map<event, HookDef[]>），每个 HookDef 带一个可选的 matcher（正则字符串）——触发时用 new RegExp(matcher).test(matcherValue) 过滤，比如只对 edit|write 工具跑某个 hook。匹配的命令并行执行（Promise.all），默认 30s 超时。

Hook 有两种语义：阻塞型（triggerBlock）任一命令返回 action:'block' 就否决该操作——这是权限门控、危险命令拦截的实现；fire-and-forget（fireAndForgetTrigger）用于 PostCompact、SubagentStop 这类不需要结果的通知场景，promise 进 pendingTriggers 集合但不 await。注意整个引擎对自身故障极度宽容：trigger 外层 .catch(() => [])、matcher 正则编译失败返回 false、监听器回调异常被吞——hook 是「增强」而非「关键路径」，绝不能因为一个坏 hook 让 agent 卡死。上面 ⑤⑥ 里 PreCompact/SubagentStart 的触发点，正是这套引擎的实际调用方。

async triggerBlock(event, args) {

function blockDecision(event, results) {
  const block = results.find((r) => r.action === 'block');  // 任一 block 即否决

⑧ Kaos：一套 API，本地 / 远程两副实现

Kaos 接口把文件系统、进程、路径抽象成一组方法（stat / iterdir / glob / readText / writeText / exec …），让上层 tool（read/write/edit/bash）对"代码跑在哪"完全无感。LocalKaos 用 Node fs/child_process，并维护实例级 _cwd 而非污染全局 process.cwd()——所以同进程里多个 agent 可以各在不同目录。SSHKaos 用 ssh2 + SFTP 把同一套 API 投到远端：exec 走 SSH channel，readText 走 SFTP。进程终止的跨平台细节也处理得很细：POSIX 用 process.kill(-pid) 杀整个进程组，Windows 用 taskkill /T /F /PID 递归杀子树；ESRCH（进程组已没）静默成功，EPERM 回退到直接 .kill()。错误体系分两支：本地 KaosError 系列，SSH/SFTP 侧 KaosSSHError 携带 SFTP status code（2=文件不存在、3=权限拒绝）。

      async for chunk in stream_llm_with_fallback(messages, tools):
          yield chunk        # 文本/工具增量实时推给前端

      # ③ 分发工具调用：mcp__{server}__{tool} 走 MCP，bash/python 走原生子进程
      results = await execute_tool_block(blocks, owner)
      messages.append({"role": "user",
                       "content": "[Tool execution results] ..."})
      if not blocks: break    # 没有工具调用 = 模型给出最终答复，收尾

几个值得抄的工程细节：（a）RAG 选工具——不是把全部 30+ 个工具一股脑塞给模型，而是用 tool_index 按最近 3 轮对话检索出 ~8 个相关工具（agent_loop.py:1274），既省 token 又减少误调用；（b）loop-breaker——用一个 _recent_call_sigs deque 检测"同一个调用签名反复出现且不产出文本"的卡死状态，触发一轮空工具的"只许回答"强制收尾（:1430）；（c）detached runs——SSE 客户端断线后，run 不会终止，而是把输出 drain 进 replay buffer 后台续跑，重连即回放，180s 无订阅者才回收（src/agent_runs.py）。

工具面非常宽：bash / python（asyncio 子进程，行缓冲流式，1 小时超时）、read_file / write_file、web_search / trigger_research、manage_memory、list_emails / reply_to_email、manage_calendar、manage_tasks（定时 LLM 任务）、serve_model / download_model（Cookbook）、以及一个能回环打任意 /api/* 的 app_api。

内建 5 个 MCP Server + 安全门控

MCP 在 Odysseus 里也是核心。register_builtin_servers()（src/builtin_mcp.py）在启动时注册 5 个：email（IMAP/SMTP）、memory（语义检索）、rag（个人文档索引）、image_gen（OpenAI 兼容画图），以及一个 npx 拉起的 @playwright/mcp（浏览器导航/截图/视觉）。其中 Playwright 只在本地 npx 缓存命中时才启动——没缓存就跳过并打日志，避免一次 fresh install 卡在几分钟的 300MB 下载上。工具用 mcp__{server}__{tool} 命名空间隔离，McpManager 走 stdio/SSE，内建 server 崩溃会自动重连。

安全模型：tool_security.py 维护 NON_ADMIN_BLOCKED_TOOLS——非 admin 用户默认拿不到 bash / python / read_file / write_file / 所有 mcp__* / 邮件 / 建模上架。检查点在 execute_tool_block：命中黑名单且非 admin → 直接返回「restricted to admin users」。无鉴权部署（单用户）则视同 admin。这意味着把 Odysseus 当多人服务暴露时，shell 与 MCP 自动收紧。

② 记忆 —— ChromaDB 向量 + BM25 关键词的混合检索，且能优雅退化

"agent evolves over time"不是口号，是一条具体的数据流。持久层是 MemoryManager（services/memory/memory.py），原子写 data/memory.json，每条带 id / text / timestamp / source / category（identity·preference·fact·contact·project·goal）。向量层是 MemoryVectorStore（services/memory/memory_vector.py），包一个 ChromaDB 集合 odysseus_memories，HNSW + cosine。嵌入可插拔：远程 OpenAI 兼容端点，或本地 fastembed（ONNX，默认 all-MiniLM-L6-v2，384 维），入库前 L2 归一化。

检索的核心是 ChatProcessor._hybrid_retrieve()（src/chat_processor.py:54）——两路打分再融合：

src/chat_processor.py — 向量 × 关键词混合融合

# 路 2：向量检索（ChromaDB 健康时才走），cosine 相似度

final *= category_boost   # identity/contact/preference 命中 ×1.2~1.4

记忆怎么"自己长"：每次 LLM 回完，后台任务 extract_and_store()（memory_extractor.py）从最近 6 条消息里用一个保守 prompt 抽取"耐久事实"（每次最多 2 条、单句、<15 词）。去重是三层防线：向量相似 ≥0.92、精确文本匹配、Jaccard ≥0.6；identity 类事实自动 pinned=True。当新增 ≥5 条时触发 audit_memories() 让 LLM 做合并归并——并用一个 SHA256 指纹跳过"内容没变"的重复审计，省掉 30–120s 的 LLM 空转。还有无 LLM 兜底：_fallback_memory_candidates() 用正则直接抓"my name is X / live in Y"，后台模型挂了也不丢身份信息。技能走平行路径：Agent 跑 ≥2 轮或 ≥2 次工具调用时，maybe_extract_skill() 把可复用流程沉淀成 data/skills/<category>/<name>/SKILL.md（带 YAML frontmatter + confidence，<0.6 丢弃）。

⑤ Cookbook —— 感知显存的模型推荐与上架（built on llmfit）

这是 Odysseus 最有"自托管特色"的能力：扫硬件 → 给候选模型打分 → 一键下载并上架推理服务。硬件探测 detect_system()（services/hwfit/hardware.py，30 分钟缓存）分平台：NVIDIA 解析 nvidia-smi、AMD 读 sysfs mem_info_vram_total、Apple Silicon 按统一内存比例算 GPU 预算（≤16GB 取 67%、>64GB 取 80%）、Windows 一条 PowerShell 拿 JSON。打分 analyze_model()（services/hwfit/fit.py）是四维加权：

失败模式 · 一个自托管系统真正的成色

Odysseus 的工程质量恰恰体现在"出错时怎么办"。三个最典型的退化路径：

🎮
GPU 检测失败

非交互 SSH shell 拿不到 CUDA 路径时，detect_system 依次重试 bash -lc 登录 shell、绝对路径 /usr/local/cuda/bin/nvidia-smi；驱动报错（nvml/版本不匹配）则置 _last_gpu_error 并退回 CPU-only 配置，Cookbook 改推 CPU 友好模型，而不是整个崩掉。

📭
IMAP 连接超时

单封 fetch 失败静默跳过、继续下一封；连接池复用前做 NOOP 健康检查，stale 连接回收重连；classify 的 HTTP 错误只打 warning 跳过该封——一个抽风的邮箱不会拖垮整个 30s 轮询。

🧬
ChromaDB 向量退化

ChromaDB 连不上 → 启动日志打 MemoryVectorStore DEGRADED，memory_vector 置 None，检索自动退回纯 BM25 关键词（权重 0.95）+ Jaccard 兜底，身份/置顶记忆仍可达——记忆"变笨"但不"失忆"。

🔌
LLM 端点抖动

llm_core 用"2 次连续失败才冷却 20s"的 two-strike 策略，单次瞬断不锁主机；请求 SHA256 缓存（128 条 LRU）+ httpx 连接池（100 连接/30 keepalive）压住重复与抖动。

对自托管 AI workspace 生态的意义

Odysseus 给"个人 AI 基础设施"画了一条和云产品不同的路：不追求最强模型，而追求"全栈本地自持"。它的价值不在某个单点——任何一块（向量记忆、Deep Research、邮件分诊、显存适配）都有更专精的开源项目——而在于把它们缝进同一个进程、共享同一份本地数据、由同一个 Agent 编排。当你的记忆、邮件、日历、文档都在本地 data/ 里，Agent 才真正"了解你"而不必把隐私交给云端。

它也诚实地暴露了自托管的现实约束：能力上限由你的显存决定——所以才需要 Cookbook 这种"先量体、再裁衣"的机制；稳定性由一堆易错的外部依赖（IMAP/CalDAV/ChromaDB/GPU 驱动）拼成——所以才有那么多优雅退化的兜底。Kimi Code 证明了"Agent 引擎不必自训模型，做好接入与编排即可"；Odysseus 把这句话推到了个人端：一个人，用自己的硬件，也能拥有一整套 ChatGPT 级的 AI 工作台——前提是你愿意接受一点 jank，换回全部的数据主权。
