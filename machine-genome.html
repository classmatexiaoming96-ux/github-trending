§ 00 · Source-level Observatory

machine-genome 模型、Agent 与 Harness 的身份谱系协议

Machine Genome 不是另一个 Agent runtime，而是一套给模型、Agent、harness、数据集和衔接产物登记身份与来源的参考实现。它把 signed genesis record 压成 Gene，再用 amendment、attestation、registry admission 和 Merkle proof 维护不可重写的谱系证据。

§ 00 · OVERVIEW

它解决什么，凭什么值得拆

▸系统定位

这个仓库的核心判断是：Agent 越来越像供应链，名称本身无法说明它由哪个模型、prompt、工具、数据集或运行策略组成。README 把目标写成 identity and provenance protocol；源码里真正落地的是 CLI 命令分发、严格记录校验、Data Integrity proof、lineage authorization、append-only registry 和透明日志。入口从 cmd/mgs/main.go:37 的 run 函数开始，命令枚举在 cmd/mgs/main.go:42 到 cmd/mgs/main.go:70，这说明作者把协议能力先做成可脚本化 CLI，而不是只给文档。

值得拆的原因在于它有清晰的信任边界：MGS 记录的结构约束在 mgs/record.go:20 到 mgs/record.go:78，签名/验签路径在 mgs/proof.go:78 和 mgs/proof.go:121，registry 入库统一落到 registry/store.go:158。同时测试覆盖了 CLI round trip、idempotent admission、equivocation、tombstone、Merkle proof tampering 和 namespace challenge，因此它不是单纯协议草案。

▸核心数据

架构模式
CLI / Go library / registry 三层，共用同一组 canonicalization、DID key、proof 与 lineage 校验函数。
核心抽象
Gene 是 secured genesis record 的 SHA-256 multihash；amendment 和 attestation 追加证据，不重写 genesis。
验证策略
入库前执行 ValidateGenesis、VerifyGenesis、VerifyLineage；之后用 Merkle inclusion / consistency proof 验证日志。
下游依赖
Go 1.24、bbolt、Ed25519 did:key、JSON canonicalization、OpenAPI 和 schema conformance scripts。

▸端到端拓扑

CLI authoring -> unsigned genesis -> ValidateGenesis -> SignDocument / VerifyDocument -> Gene(content hash) -> Store.Submit -> bbolt buckets + audit event -> Merkle checkpoint / inclusion proof -> HTTP registry + explorer

拓扑里最关键的不是 HTTP，而是 verification boundary。CLI 在 cmd/mgs/main.go:123 到 cmd/mgs/main.go:175 构造 genesis，但入库仍会经过 registry/store.go:190 的 submitGenesis；这让本地生成和远端提交共享同一套校验。测试 cmd/mgs/main_test.go:33 到 cmd/mgs/main_test.go:76 也证明 CLI 生成、签名、verify、gene 四步能闭环。

§ 03 · REGISTRY

▸统一 Submit 是 HTTP 不能绕过的 admission gate

§ 05 · RISKS

亮点之外，还有这些风险

▸协议仍处实验阶段

README 明确说 MGS 是 experimental profile。源码里也能看到实现偏向 Ed25519 did:key 和本地解析：mgs/proof.go:184 依赖 resolver.ResolveEd25519，registry admission 默认使用 DIDKeyResolver。它适合参考和试点，但要进入多组织生态，需要独立 witness、checkpoint gossip、resolver 扩展和治理流程。

▸Registry 是可信操作面，不是能力真相机

Store 能证明谁签了什么字节、这些字节如何进入日志、是否有 tombstone 或 equivocation；它不能证明某个 Agent 真的拥有声明能力。README 也提醒记录不证明 capability、consciousness、ownership 或 endorsement。工程团队若采用它，应把 registry/store.go:472 的 tombstone、registry/store.go:507 的 audit 和 registry/merkle.go:88 的 proof verification 接到自己的治理流程里。

适合借鉴
需要追踪模型、Agent、prompt、工具和数据来源的内部平台；需要 registry 可审计 admission 的多团队环境。
谨慎采用
还没有 provenance 治理流程、没有密钥生命周期管理、只想做简单 model card 展示的项目。
