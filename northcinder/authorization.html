从 pending code 到 single-use mandate 深度解析

这一页看购买权限如何从模型输出变成人类确认后的签名 mandate：code 不从 MCP 返回，fingerprint 绑定购买四元组，checkout 前再做 cryptographic verification。

2 * The explicit human approval gate (spec §4 invariant 4):
3 *
4 *   request_purchase_authorization  → PENDING authorization + human summary
5 *   approve_purchase(code)          → mandate SIGNED, authorization approved
6 *   decline_purchase                → authorization VOID (symmetric, guilt-free)
7 *
8 * The confirmation code is written to
9 * `<configDir>/pending-authorizations/<id>.code` (0600). The standard MCP
10 * runtime disables the optional STDERR banner because hosts commonly capture
11 * child-process stderr. The tool result deliberately omits the code. Another
12 * program the buyer runs under the same OS account can read buyer-local state;
13 * separate accounts are an optional local hardening boundary.
14 * Wrong-code attempts are bounded; pending authorizations expire.
15 *
16 * approval "sign what you see": both trusted channels render the FOUR-TUPLE
17 * (merchant of record, exact item + variant, all-in total with an honest
18 * unknown-tax statement, payment context per rail) plus an order fingerprint
19 * displayed WITH the code. The fingerprint commits the code to the tuple —
20 * approval recomputes it and rejects any tuple mutated after issuance — and
21 * the mandate nonce is fixed at request time so the mandate signed at
22 * approval is exactly the order the human saw fingerprinted.
23 *
24 * The purchase mandate is signed only AT APPROVAL TIME (issuance = the human
25 * act), with the user's local ed25519 keypair, binding offer id, merchant,
26 * and a hard spending cap.
27 */
