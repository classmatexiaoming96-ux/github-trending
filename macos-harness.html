§ 00 · Source-level Observatory

macos-harness 给 LLM 一台真实 Mac

browser-use/macos-harness 是一个非常薄的 Python harness：它不给每个 App 写专用工具，而是把 macOS 截屏、Accessibility、PID 定向输入、Apple Events、Browser Harness 和本地文件系统放进同一个执行面，让 Agent 在任务中自己写缺失逻辑。

§ 00 · OVERVIEW

它解决什么，凭什么值得拆

这个仓库最值得拆的地方，是它拒绝把桌面自动化做成一批应用专用 wrapper。命令入口在 src/macos_harness/cli.py:21 把 browser、mac、Path 和 subprocess 放入同一个 namespace，src/macos_harness/cli.py:31 到 src/macos_harness/cli.py:37 直接执行 stdin 代码；这说明作者把能力边界放在 Python 进程和 macOS 权限上，而不是放在一堆“Spotify 工具”“Slack 工具”的名称上。

第二个重点是安全姿态并不靠隐藏能力实现。src/macos_harness/macos.py:305 到 src/macos_harness/macos.py:323 把 Accessibility、Screen Recording、Post Events 和 Automation 分开报告或请求；src/macos_harness/macos.py:358 到 src/macos_harness/macos.py:373 又用 focus guard 阻止后台目标突然变成 frontmost。换句话说，它给模型低层原语，但仍把权限、焦点和目标 PID 当成强约束。

▸核心数据

架构模式
单进程 Python 执行面 + macOS 原语 + Browser Harness 懒连接
核心抽象
MacOS、Accessibility、BrowserHarness、LivePointerOverlay

无 benchmark；测试重点验证权限、焦点、Retina 坐标、PID 投递和隐私遥测

§ 06 · RISKS

技术亮点之外，别忽略这些

▸薄 harness 的代价是策略层缺席

源码里能看到强约束，但看不到完整策略引擎。src/macos_harness/macos.py:1449 到 src/macos_harness/macos.py:1459 暴露 AppleScript escape hatch，src/macos_harness/cli.py:31 到 src/macos_harness/cli.py:37 允许执行任意 stdin Python，src/macos_harness/macos.py:907 到 src/macos_harness/macos.py:925 允许 AX set 和 perform。生产环境需要外层审批、沙箱、日志和 allowlist。

▸macOS 权限和 App 行为仍是外部变量

它通过 src/macos_harness/macos.py:405、src/macos_harness/macos.py:413、src/macos_harness/macos.py:421 做权限前置检查，也通过 src/macos_harness/macos.py:358 到 src/macos_harness/macos.py:373 防止焦点被拉起；但 inactive app 是否接受 PID 输入、AX 树是否完整、Apple Events 是否被目标 app 允许，仍取决于系统和应用。

亮点
极薄执行面、目标 PID 输入、虚拟指针、Browser Harness 懒连接、隐私遥测测试。
风险
任意 Python 和 AppleScript 能力强，需要宿主 Agent 自己做权限审批和任务审计。
适合
本地桌面自动化、跨 App 验证、需要真实浏览器会话的 Agent 工作流。
不适合
无人工监管的高风险操作、需要跨平台一致性的 UI 自动化产品。
