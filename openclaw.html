一句话定位

OpenClaw 不是又一个聊天 App，而是一个"个人 Agent 网关"。你不需要在每个聊天工具里各装一个 bot——而是在自己的机器（Mac / Linux / 服务器）上跑一个 OpenClaw Gateway，它一头连着各个消息平台的账号，一头连着大模型与工具，把"收到消息 → 跑 Agent → 调工具 → 回消息"这条链路全部放在你自己的设备里。官方把它的理念概括为 "answers you on the channels you already use"——一个本地、单用户、常驻的私人助手。

本文基于 openclaw/openclaw 仓库的 README、目录结构与 docs.openclaw.ai 官方文档（Architecture / Skills / Plugins / ACP 等页）撰写；凡无法在公开来源中核实的内容均集中列在文末「待确认清单」，不做猜测填充。

Gateway：唯一的本地控制平面

整个系统围绕一个 Gateway 守护进程展开——它是"唯一打开 WhatsApp 会话的地方"，也是唯一持有各 provider 连接（WhatsApp 走 Baileys、Telegram、Slack、Discord、Signal、iMessage、WebChat…）、管理 session、工具、事件的中枢。所有客户端都通过它的 WebSocket API（默认绑定 127.0.0.1:18789）接入，而不是各自直连模型或平台。

┌───────────────────────────────────────────────┐ 消息平台账号 │ OpenClaw Gateway │ WhatsApp(Baileys) │ 本地守护进程 · 唯一控制平面 │ Telegram / Slack ─┼─► ┌──────────────┐ ┌────────────────────┐ │ Discord / Signal │ │ Channels │ │ Sessions / Agents │ │ iMessage / Teams │ │ 入站↔出站路由 │──►│ 多 Agent 路由 │ │ WebChat / Matrix │ └──────────────┘ │ 独立 workspace │ │ │ ┌──────────────┐ └─────────┬──────────┘ │ 控制面客户端 │ │ Tools / │ │ │ macOS App / CLI ──┼─► │ Skills / │◄────────────┘ │ Web UI / 自动化 │ │ Plugins/MCP │ ┌────────────────────┐ │ │ └──────────────┘ │ LLM Providers │ │ Nodes(role:node) │ ▲ │ openai/anthropic/ │ │ macOS/iOS/Android─┼─► WS 握手 │ │ google/...（插件） │ │ /headless 设备 │ device token └────────────────────┘ │ └────────────┬──────────────────────────────────┘ ▼ WS 协议： req {type,id,method,params} res {type,id,ok,payload|error} 事件推送 agent / chat / presence / health

连接模型分两类：控制面客户端（macOS App、CLI、Web UI、自动化脚本）以标准能力接入；Nodes（macOS/iOS/Android/无头设备）则在握手时声明 role: node 与各自的能力/命令，用于语音转发、Canvas 接入等。所有连接遵循"先握手"的 WebSocket 协议，请求为 {type:"req", id, method, params}，响应为 {type:"res", id, ok, payload|error}，Gateway 还会主动推送 agent / chat / presence / health 等事件。

设备配对与信任：新设备 ID 首次连接需配对审批，Gateway 随后签发一个 device token 用于后续连接。本机回环连接可自动放行，而经 Tailscale / VPN / SSH 隧道的远程接入则需显式批准——典型的"默认锁定、按需放宽"。

多渠道接入：20+ 平台收敛到一个 Agent

每个消息平台是一个 channel。Gateway 是唯一持有 provider 会话的进程——这意味着你的 WhatsApp 登录态、Telegram bot token、Signal 配对只存在一处，不会散落在多个 bot 里。入站消息被统一路由到对应的 Agent session，Agent 的回复再经同一渠道发回原对话/线程/话题。除主流 IM 外，文档还提到 macOS / iOS / Android 的原生支持，以及社区扩展的 Feishu/Lark、企业微信、钉钉、QQ(OneBot)、Matrix、SimpleX、甚至 Meshtastic（LoRa 离网 mesh）等渠道。

多 Agent 路由与沙箱安全模型

Gateway 支持多 Agent 路由：不同的入站渠道/对话可以路由到相互隔离、拥有各自 workspace 的 Agent。这让"私人主助手"和"群里给陌生人用的助手"能够物理隔离。安全模型据此分层：

main session（你本人） non-main session（群组/不可信来源） ┌──────────────────────┐ ┌──────────────────────────────┐ │ 工具直接跑在宿主机上 │ │ agents.defaults.sandbox.mode │ │ 完整文件/命令访问能力 │ │ = "non-main" │ │ 信任你自己 │ │ → 隔离的 Docker 容器 / SSH 沙箱 │ └──────────────────────┘ │ 不可信会话拿不到宿主机权限 │ └──────────────────────────────┘

默认情况下，主 session 的工具直接运行在宿主系统上（你信任你自己）；而当你把助手开放给群组或不可信来源时，设置 agents.defaults.sandbox.mode: "non-main"，这些会话就会被放进隔离的 Docker 容器或 SSH 沙箱里执行，拿不到宿主机的文件与命令权限。

Skills：用 Markdown 教 Agent "何时、如何用工具"

Skills 是 OpenClaw 的能力组织单元——本质是一组"教 Agent 何时该用哪个工具、按什么步骤做"的 Markdown 指令文件。每个 skill 是一个目录，核心是一份 SKILL.md：YAML frontmatter（最少只要 name + description）加 Markdown 正文，目录里还可附带脚本、模板等辅助资源。

skills/image-lab/ ├── SKILL.md # frontmatter + 正文（被注入系统提示） │ ┌─────────────────────────────────────────────┐ │ │ --- │ │ │ name: image-lab │ │ │ description: Generate or edit images via a │ │ │ provider-backed image workflow │ │ │ --- │ │ │ <markdown 正文：触发条件 / 步骤 / 工具说明> │ │ └─────────────────────────────────────────────┘ ├── scripts/ # 正文中引用的脚本 / 二进制助手 └── templates/ # 模板等附加资源 （可选 frontmatter：homepage / user-invocable / hidden / command-dispatch / command-name —— 均为单行 key）

六层加载优先级（workspace 最高 → bundled/plugin 最低）：① workspace 技能 <workspace>/skills → ② 项目 Agent 技能 <workspace>/.agents/skills → ③ 个人 Agent 技能 ~/.agents/skills → ④ 托管/本地技能 ~/.openclaw/skills → ⑤ 随安装内置（bundled） → ⑥ 额外目录与插件技能。只要某个根目录下出现 SKILL.md 就会被发现；文件夹名仅用于组织，真正的技能名、slash 命令、allowlist key 都取自 frontmatter 的 name 字段。

session 启动时会快照一份符合条件的技能清单，并在该 session 后续所有轮次中复用。技能被编译成一段 XML 注入到系统提示中，其 token 成本是可预测的——文档给出公式：195 + Σ(97 + len(name) + len(description) + len(filepath))。这种"前置注入清单、按需展开正文"的设计，正是 skills 既能多又不爆 context 的关键。

ACP：把外部编程 Agent 接进来

这里要纠正一个常见误解：OpenClaw 的 ACP 指 Agent Client Protocol（Agent 客户端协议），不是什么"Agent 之间通信协议"。它是 OpenClaw 用来驱动外部编程 harness——Claude Code、Cursor、Gemini CLI、Codex 等——的那条通路。官方明确："ACP 是外部 harness 的路径，不是默认的 Codex 路径"：原生 Codex 插件处理 /codex，而 ACP 负责 /acp 命令与 runtime: "acp" 的 sessions_spawn() 调用。

用法上先装 @openclaw/acpx 插件，再开启它：

openclaw plugins install @openclaw/acpx openclaw config set plugins.entries.acpx.enabled true # 通过 sessions_spawn 起一个 ACP 会话 { "task": "Open the repo and summarize failing tests", "runtime": "acp", "agentId": "codex", "thread": true, "mode": "session" } # 运维 / 操作命令 /acp spawn codex --bind here --cwd /workspace/repo /acp spawn gemini --mode persistent --thread auto /acp status /acp model anthropic/claude-opus-4-6

ACP 会话分三种：交互式（绑定到某个对话/线程，后续消息直接路由给该 ACP 会话，输出回到同一渠道）、一次性（父会话拥有的后台任务，完成时通过 task 通知汇报）、持久（在 bindings[] 中配置的长生命周期 harness）。绑定对话里的后续消息会自动转发给 ACP 会话，而 /acp ...、/status、/unfocus 等管理命令保持在本地、不会被当成 prompt 文本送进 harness。一个持久绑定的配置长这样：

{ bindings: [ { type: "acp", agentId: "codex", match: { channel: "discord", peer: { kind: "channel", id: "222222222222222222" } } } ] }
关键区别：ACP harness 与 OpenClaw 自己的 sub-agent 不同——sub-agent 跑在 OpenClaw 的原生 runtime（受沙箱约束）里，而 ACP harness 直接跑在宿主机上、带着它自己的 CLI 权限和文件系统访问，不在沙箱内。换言之，ACP 把"你本机已装好的 Claude Code / Codex"变成了可以从任意聊天渠道触发的远程编程能力。

插件系统与 MCP

OpenClaw 几乎所有能力都以插件形式扩展——文档原话："插件用 channels、模型 providers、Agent harness、tools、skills、speech、实时转写、voice、媒体理解/生成、web fetch、web search 以及其它运行时能力来扩展 OpenClaw"。插件有两种形态：

  • 原生插件：一份 openclaw.plugin.json manifest + 一个在进程内加载的运行时模块。
  • 兼容包：Codex / Claude / Cursor 的插件布局被映射进 OpenClaw 的 inventory，能像原生插件一样被检视、启用、禁用。

安装来源很灵活：ClawHub（clawhub:<pkg>）、npm（npm:<pkg>）、Git（git:github.com/<owner>/<repo>@<ref>）或本地目录（./my-plugin / --link）。插件策略与配置集中在 plugins 下：

{ plugins: { enabled: true, allow: ["voice-call"], # 仅放行这些插件的工具 deny: ["untrusted-plugin"], # deny 优先级最高，压过 allow load: { paths: ["~/Projects/oss/voice-call-plugin"] }, slots: { memory: "memory-core" }, entries: { "voice-call": { enabled: true, config: { provider: "twilio" } } } } }

插件通过两套 hook 注入运行时行为：typed hooks（api.on(...)，用于生命周期、中间件、策略——首选）与internal hooks（api.registerHook(...)，用于粗粒度的命令/生命周期副作用）。需要优先级、合并语义或 block/cancel 时，用 typed hooks。MCP（Model Context Protocol）在这套体系里是一等公民：插件可以挂接外部 MCP server 作为工具后端，外部 MCP server 也可经一份 JSON 配置（如 mcp_config.json）接入，让 Agent 直接调用社区/企业的 MCP 工具。

配置与部署

运行环境推荐 Node 24（或 22.19+）。最省事的安装方式是 npm 全局装包 + onboarding，它会把 Gateway 装成常驻守护进程（macOS 用 launchd、Linux 用 systemd）：

# 安装 + 引导（把 Gateway 装成守护进程） npm install -g openclaw@latest openclaw onboard --install-daemon # 最小配置 ~/.openclaw/openclaw.json （JSON5） { agent: { model: "<provider>/<model-id>", // 如 anthropic/claude-opus-4-6 }, }

除了核心 Gateway，还有可选的配套 App：Windows Hub、macOS 菜单栏 App、以及通过 WebSocket 配对的 iOS/Android node（用于语音转发与 Canvas 接入）。语音方面支持 macOS/iOS 的 Voice Wake 唤醒、Android 的持续语音模式、ElevenLabs TTS；还有 Live Canvas——一个由 Agent 驱动、带 A2UI 的可视化工作区。

源码结构：一个 pnpm monorepo

仓库是 TypeScript + pnpm workspace 的 monorepo（pnpm-workspace.yaml / tsconfig.json 在根）。顶层目录大致如下（基于仓库主分支实际目录）：

openclaw/ ├── apps/ # 各端应用实现（桌面 / 配套 App 等） ├── packages/ # 共享内部包（workspace:*） ├── extensions/ # 插件扩展（含 acpx 等；channels / providers / memory …） ├── src/ # 核心源码 ├── skills/ # 内置 Skills（SKILL.md 集合） ├── ui/ # 前端界面 ├── security/ # 安全相关代码（沙箱 / 审批 / 信任） ├── deploy/ · config/ · scripts/ # 部署 / 配置 / 工具脚本 ├── docs/ # 文档（即 docs.openclaw.ai 的来源） ├── qa/ · test/ · patches/ · .agents/ ├── pnpm-workspace.yaml · tsconfig.json · package.json └── README.md

注：顶层目录名取自仓库主分支结构；各目录内部模块的精确划分（如 src/ 下的子模块、packages/ 的具体包名）未在本次公开来源中逐一核实，见文末「待确认」。

生态与相关项目

OpenClaw（前身 Moltbot / Clawdbot）周围已经长出一个相当大的生态，核心入口是官方注册表 ClawHub。下面是可在公开仓库核实的相关项目：

  • openclaw/clawhub —— 官方 Skill + Plugin 注册表：发布、版本化、搜索基于文本的 Agent 技能（一份 SKILL.md + 辅助文件）。
  • openclaw/acpx —— 用于有状态 ACP（Agent Client Protocol）会话的无头 CLI 客户端，即上文 @openclaw/acpx 插件背后的项目。
  • VoltAgent/awesome-openclaw-skills —— 从官方 Skills Registry 中筛选、归类的 5,400+ 技能合集。
  • ComposioHQ/secure-openclaw —— OpenClaw 风格的 24×7 私人助手，借 Composio 接入 500+ 应用，带持久记忆与定时提醒。
  • kaikozlov/openclaw-signal-custom —— 由 signal-cli 驱动的增强版 Signal 渠道插件。
  • 各类 awesome 清单（LHL3341/awesome-claws、vincentkoc/awesome-openclaw 等）汇总了渠道、记忆系统、MCP 工具与部署栈。
