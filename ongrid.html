01
architecture · three bounded contexts

分层架构与三 BC

一句话定位：ongrid 把"运维 AI"拆成三个互不 import 的 Bounded Context——iam（用户/鉴权）、manager（控制面 + AIOps 大脑）、edgeagent（每台主机上的只读探针 + 执行器）。

三者通过 .go-arch-lint.yml 强制隔离，只能借 internal/pkg/**（业务无关共享层）和 api/ 通信。技术栈：Go（Chi router + cloudwego/eino agent 框架 + singchia/geminio 反向隧道）+ TypeScript/React SPA + MySQL/SQLite + frontier broker + Docker Compose。

设计哲学：深度数据查询和高危执行能力都下沉到 edge 和 specialist，coordinator 只做"派给谁 / 直接答 / 直接拒"的调度，并通过 cmdpolicy 沙箱 + ReviewGate 二审把"AI 误操作"的爆炸半径压到最小。边缘 agent 永远是发起方（dial-out）；manager 想调用 edge 的能力是通过 frontier broker 反向调用边缘已注册的 RPC handler，而非主动连边缘端口。

iam

用户 / 鉴权

独立 Bounded Context，负责身份与权限。其余 BC 不能直接 import 它，只能走 api/ 与 internal/pkg/** 共享层。

manager

控制面 + 大脑

装配 Chi handlers、IM bridge、chatruntime.Runtime（eino ReAct 图）。AIOps 全在 manager 进程内。

edgeagent

探针 + 执行器

装在每台主机上的只读探针 + 受限执行器，dial-out 连 broker，注册 RPC handler 供 manager 反向调用。

反向调用而非反向代理：manager 调边缘能力走 tunnel.Caller.Call(edgeID, method, body)，经 broker 路由到该 edge 已注册的 handler——主机上不开 22 / 80 / 443 任何入站口。

03
multi-agent · coordinator + specialist

Coordinator + Specialist 多 Agent 协作

模型：Coordinator 和 Specialist 是同一个 chatruntime.Runtime 实例里的不同 persona，区别只在 toolBag 和 system prompt。Coordinator = sess.AgentID 为空/"default"；其余 agents/*.md 里定义的都是 worker。

buildAIOpsRuntime（main.go:2376）是整个 AIOps 装配的咽喉——它把每个依赖恰好穿过一次。Coordinator 的 coordinatorToolNames（main.go:2362）被刻意收窄成只读定位 + 知识工具，注释直言这是 "rule 1 的物理执行"：coordinator 的 toolBag 里根本没有 query_promql / host_bash 这类深度工具，所以 LLM 即使想 inline 查也调不到，只能走 AgentTool 派给 specialist。

cmd/ongrid/main.go — coordinator 受限 toolBag
var coordinatorToolNames = []string{
    "query_devices", "query_incidents", "get_topology", "query_knowledge",
    "search_web", "list_repo_sources", "read_source", "grep_source",
}

派活路径：coordinator 的 LLM 调 AgentTool（PascalCase，刻意对齐 claude-code 的工具名以利模型选择，见 agent_tool.go:91）。AgentTool 是 coordinator-only 工具，tools 包不能 import chatruntime（会循环），所以它通过 WorkerSpawner 窄接口调用，由 main.go 装配处把 *chatruntime.Runtime shim 成该接口。AgentTool 默认同步派活，拿到 worker 结论后强制 coordinator 收口：

Agent loop（graph/react.go）：外层包一个 eino react.Agent，关键修正是 MaxStep = MaxIterations*2 + 2——因为 eino 把每个节点 visit 都算一步，一轮 ReAct = ChatModel + ToolsNode = 2 步，不 ×2 会让 LLM 在 30 轮上限时只跑到 ~15 轮就 ErrExceededMaxSteps。反漂移机制：每轮在 user 消息前注入独立的 <system-reminder> user-role 消息（graph/react.go:271 buildSystemReminder），内容 = 硬编码基线规则 + persona 的 critical_reminder + runtime 动态启发式（runtime.go:863 calcDynamicHints：同工具连续失败、迭代数过高、重复调用同一 (tool,args)、"承诺但没发 tool_call" 检测）。

失败模式 · 弱模型幻觉工具名：GLM-4 等幻觉出不在 schema 的工具名 → eino "tool not found in toolsNode" 直接 abort 整个图。对策：coordinator 叠加 CoordinatorStubs（redirect_stub.go）占住 host_bash / get_host_load 等高幻觉名，返回"请用 AgentTool 派给 specialist-X"而非崩溃（runtime.go:519）。
失败模式 · 重复派同一 specialist：E2E eval D1 观测到 122 次 tool call / 240s → AgentTool 用 sha256(subagent_type+prompt) 做 90s dedupe（agent_tool.go:137），命中时返回"重复派活拦截" hint。
04
tunnel · zero inbound ports

零入站端口的反向隧道 / Browser SSH

源码：internal/pkg/tunnel/client.go + edgeagent/webshell/handler.go。边缘 agent 用 gclient.NewRetryEndWithDialer 主动连 frontier broker——主机上不开任何入站口。

dial-out：首次拨号指数退避 1s→2s→…封顶 60s；连上后断线由 geminio RetryEnd 透明重连。手柄 blob Meta{AccessKey, SecretKey} 在 connect 时塞进 geminio 不透明 Meta，server 端解码后做 AuthFunc。manager 想调边缘能力时是反向 Call：tunnel.Caller.Call(edgeID, method, body) 经 broker 路由到该 edge 已注册的 handler。一个微妙坑——manager 重启会清掉 broker 路由表但 edge 的 TCP 还活着，所以 client 额外检测 broker 路由失效错误重连：

internal/pkg/tunnel/client.go — 路由失效检测重连
func shouldReconnect(err error) bool {
    msg := err.Error()
    return strings.Contains(msg, "not found") ||
        strings.Contains(msg, "mismatch clientID")
}

Browser SSH：架构经过一次重构——SSH 协议栈完全搬到 manager 侧，边缘退化成"一屏 TCP 转发器"。manager 用一个携带 {"target":"127.0.0.1:22"} Meta 的 stream 进 edge，edge 校验 target 在 allowlist 内后 dial 本地 sshd，双向 io.Copy：

edgeagent/webshell/handler.go — target allowlist
var allowedTargets = map[string]bool{
    "127.0.0.1:22": true, "localhost:22": true,
}
// localhost narrow scope 是安全边界——否则被攻破的 manager 能把 edge 当跳板打内网

manager 侧 biz/webshell/router.go 维护 SessionID → Sink 目录，把 edge 推回的 stdout 路由到对应浏览器 WebSocket；记录 per-session 字节数、支持 admin kill、idle watchdog、per-user/per-device 并发限制。SSH 口令 SSHPass 是一次性的，Dial 后从 edge 内存抹掉，永不落盘/落日志（messages.go:84 注释）。

关键设计：让 manager 独占 webshell 的 policy/audit/并发/踢人逻辑，edge 越薄越安全（无 SSH client、无 pty、无 session map）。
05
rca · correlate then trace to patient zero

根因 RCA：拓扑 + 信号关联

RCA 由两条路组成：被动（用户在 /chat 问）和主动（investigator 告警触发）。两者都吃同一个核心工具 correlate_incident——一次性把告警周围的四类信号打成一个 bundle，让 LLM 不用 chain 十次工具。

aiops/tools/correlate_incident.go — 信号 bundle
type correlateIncidentBundle struct {
    Incident    incidentSummary   // 规则名/severity/target/fired_at/labels
    Window      windowRange       // 以 first_fired_at 为中心 ±window/2
    MetricPanel []metricSeries    // PromQL range，top-3 series by magnitude
    LogPanel    []logEntry        // Loki: {edge_id} |~ "(?i)error|panic|oom|fatal|fail"
    TracePanel  []traceEntry      // Tempo: service.name 过滤
    Edge        *edgeSnapshot     // 当前 cpu/mem/up + 24h flap 计数
    Skipped     map[string]string // 哪个面板因何跳过（无 client/无 edge_id…）
    Truncated   map[string]int    // 100KB 上限时砍 logs→traces→metric values
}

PromQL 表达式由 metricExprFor 从规则的闭集 metric 名（cpu_pct/mem_pct/disk_used_pct/load1…）翻译，再用 wrapPerEdge 用 ... and on(edge_id) (group by (edge_id) ({edge_id="N"})) 限定到单台。每个子查询有独立短 deadline（trace/log/edge 互不阻塞），整体 60s 封顶，bundle 超 100KB 时按"先砍 logs 再砍 traces 最后砍 metric values"降级，并在 Truncated 里告知 LLM "你看的不是全貌"。

expand_topology

拓扑关联 BFS

在业务 topology graph 上做 BFS，默认只走"传播失败"的边（PropagatesFailure 的 relation：depends_on/deployed_on/routes_to），direction 支持 downstream（爆炸半径）/ upstream（谁导致我挂）/both。一次拉全 relation 进内存（假设 ≤10k/tenant），每个命中带 hop 数 + relation 类型 + semantics tag。

incident-investigator

因果回溯到 0 号病人

persona 把 RCA 定义成"输出一条因果链 根因→…→告警症状"而非现象摘要，强调"找最早偏离的，不是最显眼的"，用 query_change_events（产品侧变更常是 0 号病人）、expand_topology 往上游走、query_traceql 找慢 span 发起方逐层上溯。

investigator.go

主动诊断 pool

告警 first fire 时后台 spawn——3 worker + 100 buffer 的 pool，直接调 correlate_incident 拿 bundle，单轮 LLM 出 ai_initial_diagnosis Event 写回，SPA 在 incident 详情顶部高亮。完全 additive，LLM 没配/失败都静默退出，不阻塞告警 ingestion。

失败模式 · 近似匹配：incident 行只存 rule_key 不存完整 ConditionsJSON，所以 promExprForIncident 用启发式（rule_key 命中闭集名 / labels["metric"] hint / annotations hint）近似，匹配不上则 metric panel 标 skipped。
06
im bridge · bidirectional messaging

IM 双向集成：飞书 / Telegram / Slack

源码：manager/biz/imbridge/bridge.go。provider 各自的 webhook/stream handler 先验签 + 解密，归一化成 InboundMessage，bridge 保持平台无关。

inbound 流程（HandleInbound）：去重（provider:app_id:event_id，防长轮询 replay 重复应答）→ 解析 app/thread 映射（按 (im_app_id, im_chat_id, thread_id) 一聊一 session，群里所有人共享）→ /new 等命令重置 session → 发 "✦ 思考中…" placeholder → 跑 agent + 节流编辑器渐进编辑 IM 消息。outbound 渐进编辑：newStreamEditor 把 agent SSE 的 assistant chunk 节流后不断 edit 同一条 IM 消息。

飞书验签/解密（provider/feishu/verify.go）有个反直觉点——飞书 v2 events 用的是 SHA-256 拼接而非 HMAC：

imbridge/provider/feishu/verify.go — SHA-256 拼接验签
// sig = sha256(timestamp + nonce + encryptKey + body), hex
func VerifyEventSignature(timestamp, nonce, encryptKey string, body []byte, signatureHex string) error {
    h := sha256.New()
    h.Write([]byte(timestamp)); h.Write([]byte(nonce))
    h.Write([]byte(encryptKey)); h.Write(body)
    // ...
}
// DecryptEvent: AES-256-CBC，key=sha256(encrypt_key)，IV=密文前16字节，PKCS#7 去填充

长连接管理（stream_supervisor.go）：每个启用的 stream-mode IM app 一个 goroutine，30s reconcile DB——新增 app 拉起 client、禁用/密钥轮换则 cancel 重建。runClientWithRestart 指数退避封顶 60s。locale：每个 channel 可 pin locale，bridge 在 user content 后追加语言指令（localeDirective），coordinator 再透传给 specialist，避免 GLM 默认中文答英文问题。

失败模式/待确认：当前所有 IM 会话归属一个固定 service account user（serviceUserID），per-IM-user 绑定（S3）未落地（adapter.go:31）。README 提到 DingTalk/WeCom，但 provider/ 目录只看到 feishu/slack/telegram 三个实现。

mutating 纪律（cmdpolicy + ReviewGate 双闸）：

  • ① edge 侧 cmdpolicy（policy.go）：host_bash 的 binary 分五类。systemctl restart 等 write 子命令直接拒（specialist-ops.md 明说"不要用 host_bash 跑 systemctl restart 绕开二审——那条命令在 cmdpolicy 里被拒"）。ip netns exec 因为是"递归 shell 可绕过 cmdpolicy"被显式拒。shells/脚本语言/rm/dd/chmod 全在 ClassDenied。Mixed 类默认拒。
  • ② manager 侧 ReviewGate（decorators/review_gate.go）：任何 Class=write|destructive 的工具调用前，自动 spawn reviewer worker 审 proposal，只有解析到 Decision: approve 才放行内层工具；reject/解析失败/spawn 失败一律默认拒（safe default）。spawner 为 nil 时也是 "always reject"，防止误配置。
aiops/tools/decorators/review_gate.go — mutating 三态
func isMutatingClass(class string) bool {
    switch strings.ToLower(strings.TrimSpace(class)) {
    case "write", "destructive": return true
    default: return false
    }
}
// 三态：approve→跑内层+MarkExecuted；reject→ErrReviewRejected；解析不出 Decision→ErrReviewUndecided(按reject)
ReviewGate 刻意放在 timeout 外（reviewer 自己是 LLM graph，有独立 60s budget）和 audit 外（reject 没 execution 可审，写 chat_mutating_proposals 而非 execution 行）。整条装饰器链是 tenant_bind → REVIEW_GATE → timeout → audit → ratelimit → metric。

09
significance · why it matters

生态意义与技术亮点

"调度优于全能"的多 Agent 范式：coordinator 不是更强的 specialist，而是更克制的——它的 toolBag 被物理收窄到只能"派/答/拒"，深度能力强制下沉到 specialist。

这把"一个大 prompt 干所有事"的脆弱性换成了"小而专的子 agent + 明确边界"，并用 dedupe/MaxTurns/dynamicHints 一整套护栏对抗弱模型的死循环——这是把 SOTA agent 套路（claude-code 的 AgentTool/system-reminder）落到生产 SRE 场景的实践样本。

🛡 zero-trust

零信任执行面

双层闸（edge cmdpolicy 只读白名单 + manager ReviewGate 二审）让"AI 远程跑命令"从不可接受变成可审计、可回滚、爆炸半径可控。reviewer 用最强模型、default-reject、三门控。

🔌 zero-inbound

零入站端口 + Browser SSH

边缘只出站拨号，主机不开任何入站口，却仍能被远程巡检/执行/开 shell。SSH 栈收在 manager 侧让审计/并发/踢人单点可控。

🔬 rca-as-tool

RCA 工程化

correlate_incident 把 metric+log+trace+edge+变更打成单个带降级策略的 bundle，配合拓扑 BFS 和"回溯到 0 号病人"的 persona，告警诞生瞬间就产出带证据的因果链。

📦 self-hosted

自托管 + BYO-model + 多 IM

docker compose up 起全栈（含 Prometheus/Loki/Tempo/Grafana/frontier/searxng），模型层热路由 6 家 provider，IM 层 Slack/Telegram/飞书双向，避免厂商锁定。

一句话总结：ongrid 把"运维 AI"从"贴一堆 Grafana 截图让人猜"升级成"系统在告警诞生瞬间就主动产出一条带证据的因果链"，并用双层闸把"AI 远程执行"压到工程可接受的爆炸半径——它降低了团队把"运维 AI"接进现有栈的门槛。
