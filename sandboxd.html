Overview

sandboxd is the control plane for ephemeral sandboxed development environments. It runs as a single Go binary (control-plane/cmd/sandboxd/main.go) inside a Docker container and communicates with a second per-sandbox process called runtimed (control-plane/cmd/runtimed/main.go) running inside each sandbox container. The system is designed around a few core principles:

  • SQLite is the source of truth. Docker container state is converged toward SQLite, never the reverse.
  • Two-process architecture. The host-levelsandboxd controls lifecycle; the in-sandbox runtimed supervises the dev server and coding tasks.
  • Phase-gated development. The codebase is organized by roadmap phases; features behind disabled switches are nil-safe so the portable OSS build works without them.
  • Idempotent operations. Wake, reconcile, and loopback provisioning are all idempotent — safe to call multiple times.
Key invariant (CLAUDE.md non-negotiable #6): The reconciler converges Docker to SQLite. Orphan containers and orphan mounts are logged, not destroyed. A developer mid-debug who runs docker run --name s-test … by hand loses nothing.

sandboxd (control-plane main.go)

The host process is the only daemon. It owns the SQLite database, manages all Docker containers, and exposes the HTTP API. Key responsibilities:

  • Binds to0.0.0.0:9000 (OSS default) or an env-configured address.
  • Runs the boot-time Reconciler once,before the HTTP listener accepts any requests.
  • Owns theStore — a single-writer goroutine that serializes all writes through a buffered channel (capacity 64) to avoid SQLite "database is locked" errors.
  • Starts the Idle Reaper and Pressure Reaper as background goroutines after reconciler returns.
  • Builds aruntime.Client on demand for each sandbox using the host-side Unix socket path: <workspaces>/<id>.mnt/.runtimed/sock.
  • Supports SIGHUP to reload auth config without a restart.

runtimed (cmd/runtimed/main.go)

runtimed is the in-sandbox supervisor. It runs as the container's main process (PID 1 or a child). It is scoped to slice 1 of the roadmap:

  • Start and supervise the Vite dev server (pnpm dev by default).
  • Expose GET /status over a Unix domain socket on the workspace loopback (/home/sandbox/.runtimed/sock).
  • Report preview health by polling the dev server's HTTP port.
  • Detect entry-asset compile errors (blank-page detection).
  • Manage coding tasks (POST /tasks, event stream, cancel) — later slice.

The socket is bound under/home/sandbox/.runtimed/, which lives on the loopback workspace image. This means the same socket inode is reachable from inside the container at /home/sandbox/.runtimed/sock and from the host at <workspaces>/<id>.mnt/.runtimed/sock. There is no network port and no cross-tenant reachability.

Communication Protocol

sandboxd and runtimed communicate via HTTP/1.1 over the Unix domain socket. The protocol types are defined in control-plane/internal/runtime/protocol.go and control-plane/internal/runtime/tasks.go, imported by both sides:

  • GET /status →runtime.Status — runtimed snapshot (dev server state + active task)
  • POST /tasks → runtime.StartTaskRequest — start a coding task
  • GET /tasks/{id}/events → SSE ofruntime.Event — task progress stream
  • POST /tasks/{id}/cancel — cancel a task

runtimed status derivation

runtimed's probeLoop polls the dev server's HTTP port every 3 seconds. The status() method derives the runtime.PreviewState from:

Two-client HTTP design: Theruntime.Client maintains two http.Client instances — one with a 5-second timeout for status/start/cancel, and one with no timeout for the SSE task event stream. This avoids the stream being killed by a short timeout while still protecting against hung connections on command operations.

Boot-Time Reconciler

Defined in control-plane/internal/reconcile/reconcile.go. The reconciler runs exactly once at process startup, before the HTTP listener accepts any requests. This is a hard ordering requirement: a partial reconcile must never publish a half-populated egress set to clients.

What the reconciler does

It converges Docker container state toward SQLite. For every sandbox row with status running, creating, or stopped:

  1. Re-mount loopback (Phase 5 V11 fix): Kernel mount namespaces don't survive a reboot. If the .img on disk still exists and the row is not in error status, re-provision the loopback mount before deciding container state. Loopback.Provision() is idempotent — existing mounts are a no-op.
  2. Handle stale creating rows: Anycreating row older than 5 minutes is marked error (log, mark error, leave mount alone for human review).
  3. Inspect the Docker container (s-<id>):
    • Container absent → MarkStopped (do NOT auto-recreate).
    • Container present but not running → MarkStopped.
    • Container running → re-derive cgroup path and re-write memory.high (idempotent). Update row to running.
  4. Re-populate egress sources (Phase 6): Derive the live bridge IP from Docker inspect (the source of truth — Docker can reassign IPs across daemon restart). Tear down any stale entry and re-add with the current IP.
  5. Log legacy rows withoutexternal_user_id (Phase 8): A running sandbox should have one. Log a warning suggesting sandboxd backfill-legacy. Never auto-destroy.

Orphan container and mount scanning

After processing all known rows, the reconciler scans for orphans:

  • Orphan containers: Any Docker container with name prefixs- that has no matching SQLite row. These are logged only — never destroyed. The reconciler does not adopt or cull on its own.
  • Orphan mounts: Any mount under workspaces/ ending in .mnt whose base ID has no SQLite row. Also logged only.
  • Workspace owner orphans (Phase 8): Anyworkspace_owner row whose backing.img is no longer on disk. Logged; disposition is the operator's. A6-hour ticker re-checks after boot.

Memory.high re-application

When SetMemoryHigh is enabled (off by default in the portable OSS build), the reconciler re-derives the cgroup path from the container's current PID and re-writes memory.high. This addresses the Phase 1 carry-forward: "memory.high is not restored automatically bydocker start". The write is idempotent; a write failure is logged but no longer marks the sandbox errored — a running, serving container must not be torn out of service just because a soft throttle couldn't be re-applied.

Orphan Scanning Details

Orphan scanning is deliberately non-destructive. The CLAUDE.md invariant is: "SQLite is source of truth. The reconciler converges Docker to SQLite, never the other way." Orphan containers and mounts are logged for operator awareness, but the system never auto-deletes them.

Orphan container scan

The reconciler callsDocker.ListByNamePrefix(ctx, "s-") to get all container names with the s- prefix. It builds a knownIDs map from the SQLite rows it processed. Any container whose ID is not in knownIDs is an orphan: 

for _, name := range names {
    id := strings.TrimPrefix(name, "s-")
    if knownIDs[id] { continue }
    log.Warn("reconcile: orphan container (no matching sandbox row)",
        "container", name, "sandbox_id", id)
    res.Orphans["container"]++
  }

Orphan mount scan

Loopback.ListMounts() returns all mount paths under <workspacesRoot>/ that end in .mnt. The reconciler extracts the base ID (everything before .mnt) and checks against knownIDs: 

for _, mnt := range mounts {
    base := mnt[strings.LastIndexByte(mnt, '/')+1:]
    id := strings.TrimSuffix(base, ".mnt")
    if knownIDs[id] { continue }
    log.Warn("reconcile: orphan mount (no matching sandbox row)",
        "mount", mnt, "sandbox_id", id)
    res.Orphans["mount"]++
  }

Phase 7 crash debris sweep

Before orphan mount scanning, the reconciler calls Snapshot.SweepStale() which removes two classes of crash debris:

  • *.img.zst.tmp — half-written compressed snapshots from an interrupted snapshot operation.
  • *.img.bak-* — backup files from an interrupted restore.

Both are logged, not silently deleted. Counts are reported viastale_tmp and stale_bak metrics fields.

Workspace owner orphan check (6-hour ticker)

After boot, main.go starts a goroutine with a 6-hour ticker that calls CheckWorkspaceOwnerOrphans(). This iterates allworkspace_owner rows and logs any whose backing .img is no longer on disk. The function never deletes — disposition is the operator's. The check runs:

  • Once at boot fromreconcile.Once().
  • Every 6 hours from the background goroutine.

Idle Reaper

Defined in control-plane/internal/reaper/idle.go. The idle reaper is a long-lived goroutine that stops sandboxes after a configurable period of inactivity. It is Phase 5 of the roadmap.

Configuration (env-tunable)

Env varDefaultMeaning
SANDBOXD_IDLE_THRESHOLD_SECONDS2100 (35 min)Inactivity cutoff — sandbox idle after this without any activity signal.
SANDBOXD_IDLE_REAP_INTERVAL_SECONDS30How often the reaper ticks to check candidates.
SANDBOXD_WAKE_GRACE_SECONDS60Post-wake/post-SSE-disconnect grace window before idle clock resumes.

Skip rules (in-memory, per candidate)

Before stopping any sandbox, the reaper applies these checks in order:

  1. In-flight exec: Ifactivity.InflightExec.Active(sb.ID) returns true, skip. An exec is a direct signal of user activity.
  2. Explicit keepalive: If sb.KeepaliveUntil is set and keepalive_until > now.Unix(), skip. The upstream can extend the sandbox's life during long-running operations.
  3. Active coding task: If Store.SandboxHasRunningTask(sb.ID) returns true, skip. Reaping mid-task would interrupt the agent run.
  4. Open connection signal: Handled by the access-log tailer / poller bumping last_active_at within the WakeGrace window. The DB already reflects it via the ListIdleCandidates cutoff comparison.
  5. Clock-drift double-check: If !sb.LastActiveAt.IsZero() and sb.LastActiveAt.After(cutoff), skip. Safety net for clock drift.

The tick loop

func (i *Idle) tick(ctx context.Context) error {
  metrics.IdleReaperRuns.Inc()
  now := time.Now().UTC()
  cutoff := now.Add(-i.Cfg.Threshold)

  candidates, err := i.Store.ListIdleCandidates(ctx, cutoff)
  // SQL: ... WHERE status='running' AND last_active_at < cutoff
  //      ORDER BY last_active_at ASC
  for _, sb := range candidates {
    // apply skip rules...
    // docker stop s-,10s timeout
    // egress.Remove + Store.ClearContainerIP
    // Store.MarkStoppedAt
    metrics.IdleReaperStops.WithLabelValues("idle").Inc()
  }
}

Activity signals that prevent idle

last_active_at is bumped by three sources:

  • Access-log tailer — watchestraefik-access.log for requests matching the preview domain and bumpslast_active_at for the matching sandbox.
  • Open-connection poller — ifSANDBOXD_POLLER_METRIC_RE is set, polls a metrics endpoint and bumps last_active_at for sandboxes with active connections. Falls back to tailer-only if the env var is absent.
  • Wake handler — bumps on every successful wake.
  • In-flight exec tracking — bumped during active docker exec calls.

Egress cleanup on stop

When the idle reaper stops a container, it also:

  • Calls Egress.Remove(ctx, sb.ID, sb.ContainerIP.String) to drop the bridge IP from the nftables sandbox_sources_v4 set.
  • Calls Store.ClearContainerIP(ctx, sb.ID) to NULL the container_ip column on the row. This is the "every stopped sandbox has it NULL" rule from roadmap §1 DoD.

Host Memory Pressure Reaper

Defined in control-plane/internal/reaper/pressure.go. The pressure reaper defends host memory in three bands, stopping the oldest idle-running sandbox at each threshold. It is Phase 5 of the roadmap and runs on a 10-second ticker.

Hysteresis on wake refusal

The Refused atomic bool is shared with the wake admission code. It uses hysteresis to avoid flapping at the boundary:

  • Settrue whenavail < RefuseWakesPct (falling edge into 5–10% or <5% bands).
  • Cleared false when avail ≥ RefuseWakesPct + 2 (rising edge above 12%, slightly above HeadroomPct's 10% trigger).

stopOldestIdle

Picks the sandbox with the oldest last_active_at from ListIdleCandidates(ctx, now) (cutoff = now means "any row not currently being marked active"). Applies the same skip rules as the idle reaper. One stop per tick — the next tick re-reads MemAvailable and decides again. If no candidate exists, the reaper takes no action this tick.

stopHeaviestRSS (emergency <5%)

When MemAvailable falls below 5%, the reaper calls stopHeaviestRSS():

  1. Lists all running sandboxes.
  2. For each sandbox with a validcgroup_path, reads /sys/fs/cgroup{path}/memory.current via ReadCgroupMemoryCurrent().
  3. Picks the one with the highestmemory.current (RSS proxy).
  4. Calls docker stop on it regardless of activity.
  5. Logs a CRITICAL event with full row identity.

This addresses OB9 carry-forward: withmemory.high=4G and memory.swap.max=0, the kernel can stall cooperative allocators in D-state before they ever cross memory.max=10G. The pressure reaper does NOT rely on memory.events.oom_kill — it ranks bycgroup.memory.current (RSS, not OOM events). A D-state-stalled allocator counts as a kill candidate purely on those signals.

ReadMemInfo and cgroup memory reading

ReadMemInfo() (in control-plane/internal/reaper/meminfo.go) parses/proc/meminfo to compute MemAvailable and its percentage. ReadCgroupMemoryCurrent() (in control-plane/internal/reaper/cgmem.go) reads /sys/fs/cgroup{memory.current for a given cgroup relative path. Returns (0, nil) when the path doesn't exist (stopped sandbox whose cgroup has been torn down).

TaskResult Lifecycle

The coding task subsystem is built on a per-sandbox task table row (defined in control-plane/internal/store/tasks.go) and the SSE event stream from runtimed. The key design goal: a task's canonical result outlives the sandbox.

Task statuses

StatusMeaning
runningTask is active in runtimed.
succeededTask completed with a clean done event.
failedTask completed with an error.
cancelledUpstream cancelled the task via POST /tasks/{id}/cancel.

Lifecycle flow

1
POST /v1/sandboxes/{id}/tasks — upstream submits a task.

The API handler checks the sandbox is running (if stopped, delegates to the wake path first — B1 "wake-on-task-submit"). It generates a ULID as taskID, then calls runtimeClientFor(id).StartTask() which sends POST /tasks to runtimed over the Unix socket.

2
runtimed acknowledges — HTTP 202 Accepted or 409 Conflict.

If a task is already running, runtimed returns ErrTaskInProgress and the API returns 409 "task_in_progress". One task at a time is enforced by runtimed's taskMu mutex.

3
Persist the task row — Store.CreateTask().

sandboxd writes a task row inrunning state to SQLite. The row'sresult_json starts as NULL. This ensures the task result survives sandbox stops and destructions.

4
Start the result watcher — go s.watchTask(id, taskID).

A background goroutine opens the SSE stream via runtimeClientFor(id).TaskEvents(taskID, 0). It consumes events and persists the terminaldone event'sTaskResult to the row via Store.FinishTask(). The watcher closes when the done event arrives or the context is cancelled.

5
Event stream — upstream consumes via GET /v1/sandboxes/{id}/tasks/{taskId}/events.

sandboxd proxies the SSE stream from runtimed. The client sends Last-Event-ID headers for resume-after-reconnect. sandboxd translates the newline-delimited JSON events from runtimed into SSE format (id: N\nevent: type\ndata: JSON\n\n).

6
Terminal done event — carriesTaskResult.

The done event is the single terminal event. It contains the full TaskResult:status, failure_reason, files_changed, agent_message_final, build_ok, build_error_message, preview_status_after, preview_error_message, checkpoint_id, duration_ms, tokens, and timestamps.

7
Persist result — Store.FinishTask().

FinishTask(ctx, taskID, status, resultJSON) updates the row: status → terminal status, result_json → JSON-encoded TaskResult, finished_at → time.Now().Unix().

8
GET /v1/sandboxes/{id}/tasks/{taskId} — read canonical result.

Reads from sandboxd's SQLite — works whether the sandbox is still running, stopped, or destroyed. Ifresult_json is NULL (task still running), returns only the running status.

Cancel flow

POST /v1/sandboxes/{id}/tasks/{taskId}/cancel sends POST /tasks/{taskId}/cancel to runtimed. runtimed'staskMu ensures only one task runs at a time. The cancel is idempotent — calling cancel on an already-finished task returns200 OK.

Boot-time task recovery

Bothsandboxd main.go and runtimed main.go call recoverInterruptedTasks() at startup. An interrupted task is failed (never resumed). sandboxd callsserver.ReconcileTasks(ctx) which calls Store.ListRunningTasks() and marks any stale running tasks as failed before the idle reaper starts.

SQLite Store

TheStore (control-plane/internal/store/store.go) is the SQLite-backed source of truth for the sandbox lifecycle. All sandboxes, tasks, and workspace owners are stored here.

Concurrency model

A single writer goroutine reads from a buffered channel of write operations (capacity 64). Readers use db.QueryRow / db.Query directly. This avoids "database is locked" without scattering mutexes across the code. The architecture: 

type Store struct {
  db       *sql.DB
  writes   chan writeOp // buffered channel, capacity 64
  doneCh   chan struct{}
  closeCh  chan struct{}
}

Sandbox lifecycle states

StatusMeaning
creatingRow exists, container being created. If older than 5 min, reconciler marks error.

Key read queries

  • Get(ctx, id) — single sandbox by ID.
  • List(ctx) — all sandboxes, ordered by created_at DESC.
  • ListByStatuses(ctx, statuses...) — used by the reconciler.
  • ListIdleCandidates(ctx, cutoff) — WHERE status='running' AND last_active_at < cutoff ORDER BY last_active_at ASC. Ports are NOT loaded here (hot path optimization).
  • ListFiltered(ctx, externalUserID, externalProjectID) — Phase 8 external identity filtering.
  • ListAllWorkspaceOwners(ctx) — used by orphan check.
  • GetTask / CreateTask / FinishTask / ListRunningTasks — task table.
  • SandboxHasRunningTask(ctx, sandboxID) — used by idle reaper skip rule.

Key write operations

All writes are funnelled through the single writer goroutine via the writes channel. Each write is a writeOp closure executed inside the writer loop against the single DB connection. This serializes all mutations while allowing concurrent reads.

Activity columns (Phase 5)

last_active_at (unix seconds, 0 = never observed) is bumped by tailer/poller. stopped_at (unix seconds, NULL while running) records when the reaper stopped the sandbox. keepalive_until (unix seconds, NULL = no override) is the idle-reaper skip signal from the upstream.

Workspace owner binding (Phase 8)

workspace_owner is a separate table that survives DELETE /sandbox/{id}. It holds the sandbox_id → external_user_id binding for per-user purge and the Phase 8 orphan check.

Wake Handler

The wake handler (control-plane/internal/wake/handler.go) brings a stopped sandbox back to life. It has two entry points:

  • Traefik catch-all: HTTP request with Host header matching s-<id>-<port>.preview.<domain>. Returns an HTML meta-refresh that keeps the browser retrying until the sandbox is ready.
  • Programmatic JSON: POST /wake/{id} on the loopback API. Returns JSON. Used by task submission (wake-on-task-submit).

Wake flow (step by step)

  1. Per-id mutex dedup: If a wake for the same ID is already in flight, the second caller waits and reuses the first caller's outcome. This prevents double-start races.
  2. Per-id lock (Phase 7): The shared idlock.Registry is acquired for the entire wake. This excludes a concurrent snapshot/restore/destroy of the same sandbox.
  3. Row lookup + status guard: running → success (no-op). error → error response. creating → refuse (half-built row). stopped → proceed.
  4. Private sandbox gate (Phase 8): For HTML-path wakes of a visibility='private' sandbox, the preview token cookie is validated before anything else. Service/operator-authenticated callers bypass this gate.
  5. Admission check: Admit() reads host memory. If denied, returns 503 with Retry-After: 30. The wake is refused in the 5–10% or <5% bands.
  6. docker start:15-second timeout. Idempotent — safe to call on an already-running container (though the status guard above usually catches that case).
  7. Inspect + memory.high re-apply: Re-derive cgroup path from the container's PID and re-write memory.high. Failure is logged but doesn't fail the wake — the --memory ceiling still applies.
  8. Egress policy (Phase 6): Register the (possibly new) bridge IP with the nftables sandbox_sources_v4 set. Tear down any stale entry first. If nftables fails, abort the row update rather than running without egress policy.
  9. TCP-ready probe: For the catch-all path (which knows the port), poll the dev server until HTTP 200 or timeout. Timeout is informational, not a hard failure — the meta-refresh keeps retrying.
  10. Row update: Store.MarkRunningWoke() updates the row to running, setscontainer_id, cgroup_path, and bumps last_active_at.

Egress registration

Egress (nftables) is disabled in the portable OSS build (egressMgr == nil). Every consumer (reconciler, reapers, wake, API) treats a nil egress manager as "no egress policy" — exactly the default-allow behaviour. This is the single switch that keeps all of that off.

runtimed Details

runtimed is the in-sandbox supervisor. It is a single Go binary started as the container's main process. Its responsibilities in the current slice:

  • Supervise the dev server process (pnpm dev by default).
  • Probe the dev server HTTP port every 3 seconds.
  • Detect entry-asset compile errors (blank-page detection).
  • Expose GET /status over a Unix domain socket.
  • Recover interrupted tasks on startup.

type app struct {

devServer supervision

devServer.supervise() starts the dev server process, watches for exits, and restarts it with exponential back-off (capped). Each restart increments the restarts counter inPreviewState.

Startup guarantees

  • runtimeDir (/home/sandbox/.runtimed) is created with 0o755.
  • appDir (/home/sandbox/workspace/app) is created with 0o755. This self-heals sandboxes provisioned before this fix (they may have had only ~/workspace).
  • recoverInterruptedTasks() is called before accepting new work. Any stale task state from a previous stop/crash is cleaned up.

Signal handling

runtimed usessignal.NotifyContext for SIGTERM/SIGINT. On signal receipt, the dev server is stopped cleanly before runtimed exits. The context is also used to cancel the probe loop and dev server supervision.

Startup Sequence (sandboxd main.go)

The startup sequence is carefully ordered to ensure invariants hold from the first request accepted.

1
Env + dirs — parse env vars, createstateDir.
2
Open SQLite — store.Open() applies migrations, starts the single-writer goroutine.
3
Backfill last_active_at — for legacy running rows where the migration default (0) would make every existing row an idle candidate.
4
Build collaborators — docker client, loopback manager, snapshot manager, idlock registry, egress manager (nil in OSS build).
5
Reconciler.Once — runs to completion before the listener opens. All container state is converged to SQLite. Orphan mounts/containers are logged. Metrics are published.
6
Pressure reaper pre-check — if MemAvailable is already below headroomPct, run one synchronous pressure.Tick() before opening the listener.
7
Task reconciliation — server.ReconcileTasks(ctx) marks any stale running tasks as failed before the idle reaper starts.
8
Start background goroutines — idle reaper, pressure reaper, access-log tailer, connection poller, workspace_owner orphan ticker.
9
HTTP listener — httpSrv.ListenAndServe(). The reconciler has already completed, so the first request sees a fully converged state.
10
Signal handling — SIGHUP reloads auth config; SIGINT/SIGTERM triggers graceful shutdown (drain HTTP server, cancel background context, close store).

Graceful shutdown

  1. Signal handler setsgcancel() — stops all background goroutines.
  2. httpSrv.Shutdown(shutCtx) with 10-second timeout.
  3. store.Close() — drains the write channel, closes the DB.

Key Design Decisions

SQLite as source of truth

Every mutation (create, wake, stop, error) goes through sandboxd and SQLite. Docker is the execution engine, not the source of truth. The reconciler's job is to detect drift (containers that exist without rows, or rows whose container vanished) and correct the row state. It never deletes Docker objects it didn't create.

Single-writer SQLite

SQLite handles one connection at the file level. The single-writer goroutine serializes all writes through a buffered channel, avoiding "database is locked" without scattering mutexes across the codebase. Reads go directly to the read connection pool.

Idempotent everything

docker start is idempotent. Loopback.Provision() is idempotent. Egress Add/Remove handles stale entries gracefully. The reconciler re-writes memory.high on every boot. Concurrent wakes for the same sandbox are deduped by an in-memory mutex.

No auto-delete on orphan scan

The reconciler logs orphan containers, orphan mounts, and workspace_owner orphans rather than deleting them. This preserves developer debug workflows and makes the system safer to run in development alongside manual Docker usage.

Reaper skip rules prevent mid-task interruption

The idle reaper and pressure reaper both check Store.SandboxHasRunningTask() before stopping a container. The activity tailer and poller bump last_active_at so a connected browser doesn't get reaped mid-session. Explicit keepalives can extend a sandbox's life during long-running operations.

Task result outlives sandbox

The task row is in sandboxd's SQLite, not in runtimed. The result is written by the result watcher goroutine before the SSE stream closes. Upstream can read the canonical result viaGET /tasks/{id} even after the sandbox has been stopped and destroyed.

Phase-gated features are nil-safe

Egress (nftables), the snapshot subsystem, and the nginx hot-reloader are all disabled in the portable OSS build. Every consumer checksif egressMgr != nil before calling methods. The system functions correctly (with the default-allow behaviour) without any of these wired.
