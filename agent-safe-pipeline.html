agent-safe-pipeline 不可越权的 Agent 执行管线

agent-safe-pipeline 把 AI agent 的动作拆成 proposal、immutable intent、policy verdict、human approval、single-use grant 和 SafeExecutor 六段，核心原则是 agent 可以提出动作，但不能自行授权执行。

§ 00 · OVERVIEW

它解决什么，凭什么值得拆

这个仓库的主线可以从 packages/pipeline/src/intent/ExecutionIntent.ts:48 读起：ExecutionIntentSchema 把 action、target、parameters、downstreamTarget 和 idempotencyKey 固定成严格 schema；packages/pipeline/src/intent/IntentCapture.ts:32 再把 agent proposal 和可信上下文合并成 captured intent；packages/pipeline/src/intent/CanonicalIntentHasher.ts:26 用 canonical JSON 和 sha256 做绑定。换句话说，agent 只能提交“想做什么”，它不能绕过 packages/pipeline/src/decision/DecionisGate.ts:63 的 authority evaluate，也不能跳过 packages/pipeline/src/execution/SafeExecutor.ts:35 的 SafeExecutor.run。

最值得拆的是双重校验链。packages/pipeline/src/decision/DecionisGate.ts:93 会拒绝 authority 返回的 action_hash 与 captured hash 不一致，packages/pipeline/src/execution/AuthorizationVerifier.ts:64 会在执行前消费 token 并核对 decision_id、dossier_id、exp 与 intent_hash，packages/pipeline/src/execution/SafeExecutor.ts:48 和 packages/pipeline/src/execution/SafeExecutor.ts:72 还会在消费 grant 前后各重算一次 conformance。这些点让它不像一个普通 SDK，而像给高风险 agent action 准备的最小安全参考架构。

▸核心数据

架构模式
Capture → bind → decide → approve → consume → execute；执行权被延迟到 SafeExecutor 末端。
核心抽象
ExecutionIntent + intentHash + GateDecision + VerifiedAuthorization。
性能/精度数据
Intent TTL 限制在 1-300 秒，authority timeout 限制在 1-15 秒，response body 限制 100KB。
下游依赖
Shopify refund、GitHub deploy、procurement、MCP tool gate 等 examples 展示可替换 action。
本文导航 — 6 个章节依次：概述 → 架构图 → 核心模块 → 关键流程 → 测试与验证 → 风险。子页面在每个 H3 末尾以 深度阅读 → 入口展开。
§ 01 · ARCHITECTURE

不可变意图先落盘

packages/pipeline/src/intent/ExecutionIntent.ts:12 到 packages/pipeline/src/intent/ExecutionIntent.ts:64 把不可信 agent proposal 和可信运行上下文分开建模。这一步的关键不是生成 UUID，而是让后续 policy authority 拿到一个字段顺序稳定、可哈希、可审计的 binding。

▸系统拓扑

Agent proposes action ↓ IntentCapture validates proposal + trusted context ↓ CanonicalIntentHasher creates sha256 binding ↓ DecionisGate returns ALLOW / ESCALATE / BLOCK ↓ SafeExecutor consumes one-use grant before action

▸模块清单

核心模块不多，但边界清楚：packages/pipeline/src/intent/IntentCapture.ts:19 负责捕获，packages/pipeline/src/intent/CanonicalIntentHasher.ts:99 负责生成 authority binding，packages/pipeline/src/decision/DecionisGate.ts:47 实现远端 policy authority，packages/pipeline/src/execution/AuthorizationVerifier.ts:48 消费执行 token，packages/pipeline/src/execution/ActionRegistry.ts:21 把可执行动作白名单化，packages/pipeline/src/execution/ReplayStore.ts:5 防止 grant 重放。

§ 03 · KEY FLOW

从提议到一次性 grant

关键流程不是“问 policy 能不能做”，而是“让 policy 绑定一个具体 intent”。packages/pipeline/src/decision/DecisionAuthority.ts:16 的 GateDecision 保存 verdict、decisionId、dossierId、intentHash 和 authorization；packages/pipeline/src/decision/DecisionAuthority.ts:33 的 FailClosedDecision 把 authority 不可用也表示成 BLOCK。

§ 06 · RISKS & GAPS

技术亮点之外，别忽略这些

仓库是参考架构，不是完整生产系统。packages/pipeline/src/shadow/ShadowPipeline.ts:10 的 shadow mode 只有 compare 骨架，packages/pipeline/src/execution/ReplayStore.ts:5 的 InMemoryReplayStore 也明确只是进程内防重放。真实部署还需要持久化、审计、密钥轮换和 authority 高可用。

远端 authority 依赖
packages/pipeline/src/decision/DecionisGate.ts:127 catch 后 fail closed，这很安全，但也意味着 authority 不可用会阻断业务，需要 SLO 和降级策略。
内存 replay store 不够生产

14  public async claim(grantId: string, expiresAt: Date): Promise<boolean> {
15    const now = Date.now();
16    const expiry = expiresAt.valueOf();
17    if (grantId.length === 0 || grantId.length > 200 || !Number.isFinite(expiry) || expiry <= now) {
18      return false;
19    }
20    for (const [key, expiry] of this.claims) {
21      if (expiry <= now) this.claims.delete(key);
22    }
23    if (this.claims.has(grantId)) return false;
24    if (this.claims.size >= this.maxEntries) throw new Error("REPLAY_STORE_CAPACITY_EXCEEDED");
