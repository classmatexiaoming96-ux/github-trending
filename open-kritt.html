§ 00 · Source-level Observatory

open-kritt 漏洞扫描 Agent 控制面

open-kritt 是一个开源代码漏洞发现平台：前端创建 scan，后端锁定 workflow/post-script/agent skill 配置，Python engine 把仓库复制到隔离 workspace，再通过 Codex、Claude Code、Cursor 等 harness 执行多步扫描和后处理。

§ 00 · OVERVIEW

它解决什么，凭什么值得拆

open-kritt 最值得拆的点不是“让模型找漏洞”这句口号，而是它把扫描生命周期拆成可审计的状态机。入口侧的 backend/src/routes/scans.js:296 先验证模型、workflow、post-script 和 agent skill；运行侧的 backend/src/routes/scans.js:430 创建 scan 后交给 engine；界面侧的 frontend/src/pages/ScanDetail.jsx:66 和 frontend/src/pages/ScanDetail.jsx:74 持续轮询 scan 与 findings，形成用户能观察的闭环。

源码里更有价值的是约束边界。backend/src/routes/scans.js:356 用事务锁定配置资源，backend/src/routes/scans.js:405 从 workflow 与 post-script 推导必填 extra，frontend/src/pages/ScanDetail.jsx:137 到 frontend/src/pages/ScanDetail.jsx:160 用 per-record mutation queue 处理快速复核点击；这些设计说明它在做漏洞平台，而不是一次性 prompt demo。

§ 01 · ARCHITECTURE

三层控制面如何把漏洞扫描跑稳

系统拓扑可以从三个入口看：后端创建 scan，engine 消费 scan，前端展示 scan。backend/src/routes/scans.js:296 是创建入口，backend/src/routes/scans.js:468 是运行时状态修改入口，frontend/src/pages/ScanDetail.jsx:103 和 frontend/src/pages/ScanDetail.jsx:116 把这些能力映射成暂停、恢复、保存运行设置。

▸系统拓扑

[CreateScan UI] -> POST /api/scans -> lock workflow/post-scripts/agent-skills -> Scan(status=pending|queued) -> Worker.process_scan -> prepare workspace + render prompt -> model harness run -> validate structured output -> post-processing: dedupe -> rank -> post-script -> ScanDetail polling + human review

▸模块清单

四个模块最关键：API 层负责参数和资源锁，queue 层根据 workflow depth 生成 pending jobs，workspace 层复制隔离仓库和依赖，post-processing 层把模型输出变成可复核漏洞清单。backend/src/routes/scans.js:103、backend/src/routes/scans.js:120、frontend/src/lib/scanPresentation.js:29 分别说明配置锁、运行时更新和复核摘要不是 UI 附属品。

API 控制面
创建、暂停、恢复 scan，并在事务里锁定 workflow/post-script/agent skill。
Engine Worker
消费 scan 状态，生成 pending jobs，处理 rate limit 和 post-processing。
Review UI
轮询 scan 与 vulnerability，使用 mutation queue 避免快速复核覆盖。

§ 03 · KEY FLOW

从创建 scan 到 post-processing 的关键流

关键流里有两个容易被忽视的边界：scan 何时从 running 进入 post_processing，以及用户复核如何在轮询中保持最新写入。前者由 engine 的 job 完成情况驱动，后者由 frontend/src/pages/ScanDetail.jsx:137、frontend/src/pages/ScanDetail.jsx:145、frontend/src/pages/ScanDetail.jsx:150 到 frontend/src/pages/ScanDetail.jsx:160 的 mutation queue 覆盖处理。

▸扫描生命周期状态机

queued/pending -> prewarming_cache -> running -> post_processing -> completed | paused/stopped/failed rate_limited -> scheduled retry -> pending

▸复核与后处理流水线

raw vulnerabilities -> semantic dedupe batches -> bounty ranker batches -> post-script enrichments -> API serialize -> ScanDetail optimistic review

§ 06 · RISKS & GAPS

技术亮点之外，别忽略这些

open-kritt 的风险主要来自三处：模型 harness 是外部进程，workspace 会复制用户仓库，post-processing 又会继续调用模型做去重和排序。backend/src/routes/vulnerabilities.js:34 的人工复核接口很克制，但 engine 的运行成本、凭据隔离和错误恢复仍是上线时要重点压测的部分。

凭据与 workspace 隔离成本

workspace 准备会创建 job home、复制凭据、设置 HOME/CODEX_HOME/CLAUDE_HOME。虽然 backend/src/routes/scans.js:423 记录 dependenciesDetail，frontend/src/pages/ScanDetail.jsx:253 展示 commit，但真正的安全边界在 engine 侧，需要部署者认真配置容器和 token 权限。

后处理仍会消耗模型额度

post-processing 不是免费整理，它会继续做 dedupe、ranker、post-script。前端 frontend/src/pages/ScanDetail.jsx:206 展示 rate limit，frontend/src/pages/ScanDetail.jsx:1176 标记 rate_limited，但团队仍需要设置 worker cap 和重试策略。

75 * their source depth in the key, so valid references to moved batch boundaries
76 * are renumbered at the same time.

78export function insertWorkflowDepthBefore(builder, depth, newStepId) {

80  if (!Number.isInteger(depth) || !builder.levels.some((level) => level.depth === depth)) {

82  }

88      .filter((level) => level.depth > 0 && level.consumesAll && level.depth >= depth)
89      .map((level) => [level.depth - 1, level.depth])

102    schema: [],
103    steps: [{ id: newStepId, name: 'New step', content: '' }],
104  });
